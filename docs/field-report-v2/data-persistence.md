## 0. Orientation + independence declaration

**Target.** `crates/core/` is pumper's single data crate: `storage.rs` (3,388 LoC durable job queue), `datasets.rs` (4,566 LoC change-detection + record store), `cache.rs`, `costs.rs`, `tiers.rs`, `retention.rs`, `backup.rs`, `doctor.rs`, plus **40 forward-only `.sql`** migrations under `crates/core/migrations/`. Stack: **sqlx 0.8 (SQLite/WAL)**, `chrono`, `uuid`, `serde_json`. One `SqlitePool` (`max_connections(8)`), shared with every sibling store (`storage.rs:205`).

**This is a genuinely independent stack from the corpus.** Every corpus leaf in this shard is authored *from Personas* — they cite `incremental.rs`, `db/src/repos/`, `ts-rs`, `src-tauri`, `run_incremental`, `DbPool`. Pumper shares **none** of those primitives: it is **sqlx (not rusqlite)**, **forward-only numbered `.sql` files with a checksummed ledger (not `run_step` convergence)**, **axum server (no ts-rs / TypeScript boundary in `core`)**. So where pumper agrees with the corpus physics it is an **independent rediscovery**, which is the strong-evidence case the kit asks for.

**Entanglement, stated up front (kit rule 2).** No leaf in *this* shard names "pumper" (grep of the 29 leaf docs + `situation-spine.md` + `shared-facts.json`: 0 hits; the only two corpus files that mention pumper are in *other* shards). **However**, four of my leaves — `backfill-migration`, `post-write-side-effects`, `derived-index-sync`, `conditional-write` — make **anonymous** "two/three sibling repos independently rediscovered this" convergence claims, and pumper is a plausible-but-unconfirmed member of those cohorts (the `backfill` head's "one of them stating it as its design principle in a comment" is a near-exact match for pumper's `0020` comment). I therefore score those four `holds` but flag them **`holds` (possible convergence-sibling)** in the notes rather than claiming a clean independent hold. Pumper keeps **its own** pattern ledger (`.perfect/Architect/strong-patterns.md` / `weak-patterns.md`), separate from Personas' golden-path corpus — the two are not one ledger.

**Maturity note.** Pumper is a young, single-writer server. Three corpus subsystems it has simply not built (DB query-latency ring, DB-backed settings store, field-level partial-update API) are scored **`n/a-absent`**, not as failures.

## 2. Deviations (nothing applied — read-only run)

Ordered by severity. None is a `violates`; all are `partial` with a stated "held: reason".

**D1 — `jobs.status` has no CHECK constraint (`status-transition-rules`, sev: medium).**
`0001_init.sql:5` declares `status TEXT NOT NULL DEFAULT 'queued'` with no `CHECK (status IN (…))`. Probed: `INSERT … status='BOGUS_STATE'` is **accepted**. The Rust `JobStatus` enum + single-door writer are the only guards. Contrast `sources.state` (`0020:27`) which *does* carry the CHECK (probed: rejects `'BOGUS'`). *Held: pumper is single-writer and every transition goes through `storage.rs` guarded UPDATEs, so the illegal-route risk is a migration/repair-script writing raw SQL — real but low-frequency. Fix is one line in a new migration (rebuild-in-place like `0021`, or the states are stable enough to accept the residual risk).*

**D2 — 0 foreign keys, and parent-naming columns are undocumented (`foreign-key-policy` / `delete-semantics`, sev: medium).**
No `REFERENCES` anywhere (probed). `jobs.schedule_id`/`trigger_id`/`source_job_id` and many `*_id` columns are bare TEXT. *Held: intentional — a job-queue wants children (audit/lineage) to outlive parents, and pumper hand-manages the few real cascades (retention pin-graph, soft-delete). The corpus itself sanctions FK-free audit columns.* The actual gap is that the corpus's mitigation — an explicit `-- RETAINED BY DESIGN:` comment on each FK-free parent column so "no FK" reads as a decision, not an oversight — is absent. Cheapest fix: annotate, don't add FKs.

**D3 — pool pragmas are never read back (`connection-pool-pragmas` clause c, sev: low-medium).**
WAL + `busy_timeout(5s)` are set on `SqliteConnectOptions` (`storage.rs:176-184`) but never verified. The corpus's clause (c) — "read `journal_mode`/`foreign_keys` back and log an error if not `wal`/`1`" — is the one thing ports drop, and `backup.rs`'s WAL-consistency argument *depends* on WAL actually being on. *Held: sqlx applies these deterministically per-connection and a WAL failure would surface fast in practice; FK-readback is moot (0 FKs). Four lines would close it.*

**D4 — `params` JSON swallowed in the row mapper (`row-to-struct-mapping` / `json-blob-column`, sev: low).**
`storage.rs:2614` maps `params` with `serde_json::from_str(&r.params).unwrap_or(Value::Null)`. On a `NOT NULL DEFAULT '{}'` column this should never fire, but a corrupt manual write silently becomes `Null` — losing the job's *input*. The status/uuid/timestamp fields all propagate correctly, so this is the one field where the mapper "decides". *Held: the column's `NOT NULL` + all-writes-through-Rust make corruption near-impossible; but the corpus rule is "decode through one named `[data,error]` function; a decode failure never silently substitutes."*

**D5 — `id TEXT PRIMARY KEY` omits `NOT NULL` (`id-generation`, sev: low).**
Probed: a `NULL` id row inserts successfully (SQLite quirk — non-INTEGER PKs allow NULL unless `NOT NULL`). *Held: every id is minted `Uuid::new_v4()` in Rust before insert, so the column is never actually null. One-word DDL edit removes the footgun.*

**D6 — 2 `INSERT OR IGNORE` on content-addressed tables (`upsert`, sev: low).**
`datasets.rs:1913` (`rules_versions`, hash PK) and `storage.rs:1435` (`saved_search_seen`). The corpus says never `OR IGNORE` (it swallows `NOT NULL`/`CHECK` violations alongside the intended duplicate). *Held: both are content-addressed idempotent inserts where the swallow surface is bounded; `ON CONFLICT(hash) DO NOTHING` would name the constraint and is a mechanical swap.*

**D7 — `now_utc()` helper duplicated ×6 (`timestamp-storage` ergonomics, sev: low).**
Identical `to_rfc3339_opts(SecondsFormat::Micros,true)` in `storage`, `cache`, `costs`, `datasets`, `tiers`, `recipes`. Physics holds in every copy; the DRY risk is one copy drifting precision and breaking the byte-sortable invariant six stores rely on. *Held: all six are byte-identical today.*

## 4. Methodics

- **Executed vs shallow.** 20 leaves deep (executed a DB probe or read ≥2 implementations); 6 head+one-check; 3 n/a-absent (confirmed absence by grep, not asserted). Executed DB work: built a throwaway SQLite from all 40 migrations (`sqlite3 3.50.6`), independently re-checked table count (30) and FK count (0) two ways (`pragma_foreign_key_list` per table **and** grep of the `.sql`), and proved four constraint behaviors by hostile insert (bogus `jobs.status` accepted; bogus `sources.state` rejected; NULL `id` accepted; duplicate `idempotency_key` rejected while multiple NULLs allowed). Throwaway DB deleted-on-overwrite in scratch; no repo DB touched; **no `cargo` run** (kit rule).
- **Two-implementation agreements.** FK count cross-checked two ways → both 0. Migration op-histogram (35 ALTER / 30 CREATE TABLE / 30 CREATE INDEX / 3 DROP) cross-checked the "additive-only except one rebuild" claim against the direct `DROP TABLE` grep (only `0021`) → agreed.
- **Self-corrections.** (1) Initially leaned `n/a-scope` on `foreign-key-policy`; corrected to `partial` after confirming the corpus explicitly names *undocumented* FK-absence as the failure mode, not FK-absence itself. (2) Initially read `to_rfc3339_opts(Micros)` as a *deviation* from the corpus's `Millis`; corrected to `holds` (both are fixed-width/zone-terminated/byte-sortable — precision is calibration, not physics). (3) Nearly scored `destructive-schema-change` as thinly-evidenced; corrected after realizing the leaf's central hazard is **n/a** under a forward-only+checksummed model, which is itself the finding.
- **Instrument gaps.** Corpus `index.json` carries no `in_corpus` field — it is an inventory of what *exists* (205 docs), so the four-state `in_corpus` framing in §3 is my judgment against the leaf text, not a lookup. sqlx's `_sqlx_migrations` ledger could not be observed in the throwaway DB (I applied migrations with `sqlite3` directly, not the sqlx migrator, to avoid a `cargo` run) — the checksum/immutability behavior in E2 is cited from `sqlx::migrate!` semantics + `backup.rs:141`'s reader, not from an executed migrator run. The four "possible convergence-sibling" flags in §1 could not be resolved to a confirmed yes/no without the corpus authors' sibling roster (the leaf heads anonymize it), so they are flagged, not counted as `holds(self)`.
