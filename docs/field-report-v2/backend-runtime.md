## 0. Orientation + independence declaration

pumper is a Rust workspace: an axum HTTP service (`crates/server`) over a durable SQLite/WAL job queue (`crates/core`, sqlx) with pluggable engines (`engine-http`, `engine-browser`, `engine-claude`, `engine-wasm`, `engine-search`, …) and ~30 scraper "apps". It is a **headless, single-process, single-tenant, localhost-first** service. There is **no** Tauri, no React/TypeScript frontend, no product-tier system, and no per-user authentication on the main REST surface (localhost trust; two *external*-facing doors — signed webhook ingress and the peer fetch fabric — carry their own credentials).

**Independence declaration.** pumper keeps **no** census/rules ledger against Personas and shares no lineage with the golden-path corpus; none of these 43 leaves was authored *from* pumper (the corpus is authored from the Personas Tauri app). Every `holds` below is therefore an **independent** hold — the strongest evidence class the protocol defines — and there are **zero `holds(self)`**. Where a corpus clause is Tauri-IPC-shaped, I translated the physics to the HTTP-route analog (an inbound command surface, its authorization, its validation) and marked `n/a-scope` only where a clause is genuinely Tauri-specific.

Because pumper is single-process/single-tenant, several corpus subsystems (product tiers, session tokens, cloud auth, multi-instance leader election, a calendar UI) are **absent by maturity/scope, not failed** — kept in the `n/a-absent` column per rule 3.

## 2. Deviations (nothing applied — read-only run)

**D1 — `credential-injection-into-child` — VIOLATES — severity Medium-High.**
`engine-claude` (and `engine-browser`) spawn their child with no `.env_clear()`/`.envs(sanitized)` — grep across all three engine crates returns zero env-manipulation sites. The child therefore inherits pumper's full process environment, which via `.env` loading (`main.rs:407-424`) can hold `ANTHROPIC_API_KEY`, `CENSUS_API_KEY`, the Sentry DSN, and webhook secrets. The Claude engine's job is to run a model over **untrusted scraped content**, so an indirect prompt-injection that induces the CLI (or an MCP tool it invokes) to read and echo `env` is a realistic exfiltration path. The corpus physics is exactly "never inherit and subtract; build the child's env deliberately." *Held: reason* — the CLI is first-party and legitimately needs `ANTHROPIC_API_KEY`, and `engine-wasm` (the untrusted-plugin host) is already a sandbox with no ambient env; but the fix (`.env_clear()` then add back only `ANTHROPIC_API_KEY` + `PATH` + what the CLI needs) is cheap and closes the injection surface. Recommend flagging for the security lane.

**D2 — `retry-with-backoff` (webhook) — partial — severity Low-Medium.**
The webhook dead-letter drain uses a deterministic fixed schedule `DRAIN_BACKOFF_SECS=[30,60,300,1800,7200]` with no jitter, and the in-process send loop is linear `2*attempt` with no jitter. Many deliveries failing at once (an endpoint outage) will all wake to redeliver on the same boundaries — the thundering-herd the corpus's "put the randomness in" clause exists to prevent. The sibling `engine-http` already has jitter, so the fix is a known local pattern (`webhook.rs:588-629` vs `engine-http/src/lib.rs:549-551`). *Held: reason* — `DRAIN_BATCH=20`/tick already rate-caps the herd, and `[30,60,…]` steps are coarse, so real-world collision is bounded.

**D3 — `domain-event-publication` — partial — severity Low.**
`JobEvent.status` is a free-form String with values as scattered string literals across `worker.rs`/`ingress.rs`/`progress.rs`; there is no central vocabulary (unlike the adjacent `TRIGGER_OUTCOMES`/`DELIVERY_STATUSES` constants). A typo'd status literal is invisible until a subscriber's `matches!` silently fails to match. *Held: reason* — the bus is ephemeral SSE observability and the durable reactive path (triggers) is idempotent+ledgered, so a wrong literal costs a missed dashboard update, not lost work. Enrichment candidate (centralize the vocabulary).

**D4 — `trigger-wiring-surface` — partial — severity Low.**
`create_trigger` validates the target app and the kind vocabularies but deliberately does **not** validate the *source* app/dataset against known emitters (to allow virtual namespaces), so a mistyped `source_dataset` is accepted and simply never fires — a silent no-op rather than a door refusal (`routes/triggers.rs:172-218`). *Held: reason* — deliberate design; `GET /triggers/{id}/runs` surfaces the empty ledger, so it is diagnosable.

**D5 — `backfill-window-replay` dedupe — partial — severity Low.** Missed-slot advancement dedupes by prior-read (moving `last_run`/`last_skipped_at`) rather than a uniqueness constraint on a slot key. Safe under the single-loop scheduler; would need the UNIQUE key if a second scheduler instance were ever introduced.

**D6 — `loop-ownership-and-restart` — partial — severity Low (latent).** `recover_stuck` re-queues **all** `running` rows at boot with no instance fence; correct for one process, double-runs work if two processes share the DB. Latent until multi-instance is attempted.

## 4. Methodics

- **Executed vs shallow.** 28 leaves deep-dived with an executed check (direct file reads + `grep` structural scans + two DB-**schema** probes against the migrations: the partial UNIQUE `idx_jobs_idempotency` and the `idx_jobs_claim`/`heartbeat_at` columns). 15 resolved shallow (head + one targeted grep). No leaf was scored from the head alone without at least one repo-grounded check; nothing fabricated. I did **not** run `cargo`, build, or any mutating command (standing rule), and did not need a throwaway DB — the migrations + code proved the behaviours directly.
- **Two-implementation checks.** (a) `retry-with-backoff`: `engine-http` and `webhook` **disagree** — the former jitters, the latter does not. This disagreement is the finding (D2), not noise. (b) `idempotent-invocation`: cross-checked three doors (HTTP enqueue, ingress event-id, trigger hops) — all consistent on "derive the key from the request, dedupe, tell the caller which branch." (c) route/error inventories cross-checked against their own drift-gate tests.
- **Self-corrections.** I first read `scheduled-trigger-firing` as a candidate *violation* (no persisted `next_trigger_at` at all).
