# App fleet & domain datasets

Apps are `ScrapeApp` implementations under `crates/apps/*`, registered in `crates/server/src/registry.rs` (adding one: crate + workspace dep + server dep + one registry line). `GET /apps` lists name/description/schedule/requires/ready plus **`default_params`** (the machine-readable defaults); each description documents its params in prose too. `requires` is the app's static preconditions (today `env:<VAR>` credentials) and `ready` is whether all of them hold — where **a variable set to a blank or whitespace-only value counts as missing, not as satisfied**. A bare `CENSUS_API_KEY=` in `.env` is what a human writes before they have the key, and the loader sets it verbatim, so treating "set" as enough reported the app ready and offered it in the MCP tool list (which filters on this same flag), turning a known gap into an upstream 403 on the first job. A `POST /apps/{name}/jobs` body's `params` **shallow-merges over `default_params`** — setting one key keeps the rest of the defaults, so a manual run matches its scheduled twin (a non-object `params` replaces wholesale).

| `watch` | Visualping-style URL monitor: fingerprint (title/chars/sha256/600-char excerpt) into `pages` keyed by URL; result carries ChangeKind + field diff. Compose with `/schedules` + `/watches`.<br>**An empty extraction is not a page change (2026-08-14):** a fetch that yields no readable content now **fails the run** — no `pages` record, no revision, no alert — instead of fingerprinting the empty body. It used to store `{chars: 0, content_sha256: e3b0c442…, excerpt: ""}` as a `changed` revision, so every subscribed webhook fired "the entire page vanished" and the next healthy run fired a second, equally false alarm: two false alarms per incident, on the one app whose value is that its alarms mean something. Escalation on `min_content_chars` is best-effort (the ladder returns the last tier's body however thin), so an interstitial, a JS-only shell or an empty 200 reached that path routinely. The predicate is `pumper_core::extract::extracted_nothing`, shared with `readable` — apps may not depend on apps, so it was lifted to core rather than copied a third time, and the field-level `is_blank` delegates its string arm to it so document- and field-level "nothing" cannot drift apart. It is a guard, not a policy knob: there is no `min_chars` param, and a one-character page is content. The error names the URL, engine and status, so a site that really serves a near-empty page stays diagnosable. |

| `research` | Agentic web research via the Claude engine (roles: `research` = Sonnet @ effort `high`, `compose` = Opus @ `xhigh`); JSON report. `session_id` param **resumes** a prior run to drill down on its accumulated context (the query becomes a follow-up) instead of re-paying the full agentic loop. `max_budget_usd` is a **run total**, not a per-call cap: it is enforced against the run's cumulative spend (including spend restored from a checkpoint), every step is issued with only the remaining headroom, and a run with under a cent left stops with `stop_reason: budget_exhausted` and returns its partial findings. `max_turns` is likewise a run total; each step is charged `min(reported num_turns, that step's cap)`, because the CLI's counter is not unambiguously per-invocation on a resumed session. The `report.json` artifact write is best-effort (a filesystem failure is logged, never costs a paid re-run). Result: `{query, topic, report, structured, resumed, resumed_from_checkpoint, steps, cost_usd, duration_ms, num_turns, session_id, stop_reason, datasets, snapshots, watch_requests, watch_requests_truncated, sources_truncated, index_datasets}` — `report` is an object `{summary, key_findings, sources}` only when `structured` is true, otherwise a raw string; `steps`/`cost_usd`/`duration_ms`/`num_turns` are cumulative across resumed attempts; `resumed` means the caller named the session while `resumed_from_checkpoint` means the runtime re-claimed an interrupted attempt. Contract pinned by `crates/apps/research/tests/result_contract.rs`. Every structured run also **writes datasets**: `research/findings` (one record per key finding, keyed `{slug(topic)}#{i}`) and `research/sources` (one per cited URL), provenance-stamped and declared in `index_datasets`; `snapshot_sources` archives each citation through the metered tiered fetcher and stamps `artifact_sha`, `watch_sources` creates one `watch` schedule per citation (`managed_by = "app:research"`, capped by `[worker] max_app_schedules_per_run`). See [§research: a living knowledge base](#research-a-living-knowledge-base) |
| `provisioner` | **Proposal compiler**, not a provisioner: one sentence (`prompt`) → a reviewed `[[source]]` proposal. Researches 1–3 candidate URLs via the Claude engine, samples each through the tiered fetcher (`to_markdown`, archive tier at `sample_archive_max_age`, default 86400s; API recipes on), drafts a declarative `RuleSet` against the primary sample and **dry-runs it through the real extraction engine**, repairing up to `max_iterations` (default 2, cap 5). Emits one record per prompt into **`provisioner/proposals`** (key = the slugified prompt, so a re-compile is a revision, not a duplicate), plus `proposal.json` and `sample-N.{html,md,txt}` artifacts. Record: `{prompt, catalog_row, catalog_toml, rule_set, seeds, samples, cadence, budget, sample_stats, confidence (0–100), confidence_scale, catalog_confidence (1–5), accepted, verdict, provisioned, intended_dataset, iterations, cost_usd}`. **`samples`** carries, per seed, the fetch tier that actually won, which `FetchOutcome` field held the body, its byte count and a `tier:verdict` trace.<br>**Scoring is per-document.** The draft is written against the primary sample, so the accept bar reads *that document only*: a strict majority of its fields must **hold** (the rule bound, and the transform chain did not reduce the value to nothing). The other candidates are **held-out evidence** — `sample_stats.held_out[]` reports `{url, fields_held, fields_total, fields_missing}` per candidate — and never enter the bar, because they are different sites with different markup and adding one must not move the pass threshold. `confidence` is the share of the primary document's fields that hold. **Three degenerate drafts are rejected deterministically**, before any repair spend and whatever the match rate, with the reason in `sample_stats.rejections[]` and the top-level `rejections`: a rule set of nothing but `const` rules (constants always bind, so it would score 100 while reading nothing off the page); an `each` field yielding **0 items on every** document examined (`ContainerEmpty` is not a miss for a *proven* selector, but a draft has no track record); and a field whose selector matched an element the transforms could not coerce (`to_number` over `"Add to cart"` — the wrong-element signature, which the engine has always computed and the dry run used to ignore). A rejected draft scores `confidence = 0`. **The emitted row is inert by construction**: `status = "planned"`, empty `cron`, `app = ""`, `access = "scrape"`, `engine` = the tier that really served the sample, `confidence` on the catalog's documented 1–5 scale, and `dataset = "proposed:<key>"` — a marker, not a resolvable `<app>/<name>` path, because nothing writes it yet. A **rejected** dry run still emits a record, marked `verdict: "rejected"` in the record *and* `REJECTED` in the row's own `notes` (the pasteable TOML fragment is the only artifact a reviewer may read). The metered discovery stage is checkpointed, so a reaped/suspended compile resumes without re-spending it. Params: `{prompt (required), budget_usd, max_iterations, sample_archive_max_age}`. On-demand only — no schedule. The record also carries a `status` field (`planned` at compile time) driven by the `GET/POST /provisioner/proposals...` lifecycle routes — see [http-api.md § Provisioner proposal lifecycle](http-api.md#provisioner-proposal-lifecycle-provisionerproposals) and "Known gaps" below |
| `transact` | Execute a declarative browser flow to the confirmation state and emit an evidence bundle; with `submit: true` it stages an approval and parks, and an approved commit performs the one irreversible action. See [§ `transact`: evidence, approval, submit](#transact-evidence-approval-submit) |
| `hackernews` | HN front-page stories into a change-detected dataset (`stories`, keyed by HN item id). Params `{pages: 1-5}` (30 stories/page). The template app for classic fetch-and-parse, and the app `just smoke` drives end to end.<br>**A partial parse cannot tombstone (2026-08-14):** the write is a full-snapshot `sync_many`, so a run that read 15 of the 30 story rows the page served used to tombstone the other 15 and report success — the empty-parse guard only catches 0-of-N. HN publishes no total, but the page states its own extent: `tr.athing` rows *served*. The run now reports `rows_seen` and a `parse {rows_seen, parsed, skipped, skipped_no_title, skipped_no_id, share, floor, partial}` block, and when `parsed ÷ rows_seen` is below the floor (1.0) the write is **downgraded to an upsert** with `removals_suppressed` naming the shortfall — the smlouvy/cordis pattern. Deliberately judged on parsed-÷-served and **not** on "did the page serve 30 rows": a genuinely shrinking front page serves fewer rows that all parse, and that still tombstones (otherwise the app would be permanently upsert-only in the one case removal exists for). A short page is *reported* in `warnings[]`, never gated on.<br>**`removed` is emitted, and id-less rows are dropped:** the result carries `removed` (it promised tombstoning in `output_shape` while emitting only `{count, new, changed, unchanged, stories}`, so a run that removed 15 stories and one that removed none were byte-identical). A row with no `id` attribute used to be keyed `rank-{n}` — rank is positional, so each run's `rank-7` overwrote a *different* story and manufactured a fake `changed` revision; such rows are now skipped and counted in `skipped_no_id`, which feeds the floor. `id` is consequently never null in a `stories` record. |
| `connector-api-watch` | Watches Anthropic API docs pages: diff + summarize + alert |
| `smlouvy-dump-watch` | Watches the Czech **Registr smluv** bulk-dump index (`data.smlouvy.gov.cz/index.xml`) → one change-detected record per monthly dump (year/month/sha1/size/URL) in `dumps`, keyed by dump URL and **full-snapshot synced** so a re-generated month surfaces as `changed`. Does not download the ~100 MB dumps; `year_from` trims the ~100-dump history. A `dataset` trigger on `fresh` fans a targeted re-download. Daily 05:30. Serves tender-radar (a sibling product), so it's outside Pumper's grant/labor catalog.<br>**A partial parse cannot tombstone (2026-08-14):** the sync is a full snapshot, so a feed publishing 51 dumps of which 30 parsed used to tombstone the 21 keys it had merely *failed to read* — and report the same numbers as a clean run, because `dumps_in_index` was the **post-parse** count. `dumps_in_index` now means `<dump>` blocks **seen**; `dumps_parsed` and the `parse: {blocks_seen, parsed, skipped, skipped_missing_url, skipped_unparseable_date, share, floor, partial}` block report what was read out of them, so a 30-of-51 run is distinguishable from a 30-of-30 run. Below a **parsed-share floor of 1.0** the write downgrades from `sync_many_*` to `upsert_many_*` and says so in `warnings[]` and `removals_suppressed`. The floor is deliberately tight because the index is small, machine-generated and schema-stable since 2016 (a skipped block is drift, not noise), and because the two errors are asymmetric: suppressing a removal costs a stale pointer to a retired month, while a wrong tombstone costs a downstream consumer its entire dump index. A genuinely **shrinking** feed still parses 100% of its blocks, so it still syncs and still reports `removed` — only a *garbled* feed suppresses removals. **A year window cannot tombstone either (2026-08-14):** `year_from` filters what is *tracked*, never what the index was seen to hold — so the parse floor is judged on the parse and structurally **cannot** see the window. A clean 120-of-120 parse read through `year_from: 2024` has `share: 1.0` and `partial: false`, sailed past that floor, and then tombstoned the ~96 pre-2024 dumps it had merely *scoped out*. Worse, they came back: `dumps` is **one shared dataset**, so the daily unwindowed run and any windowed consumer run alternated deleting and resurrecting them, and every resurrection lands in `fresh_dumps` — which a `dataset` trigger fans out as a targeted re-download of ~100 MB files, i.e. ~10 GB of downstream traffic per flip. A window that **actually excludes** dumps now downgrades the write to upsert-only and names itself in `removals_suppressed`; a window that excludes nothing (`year_from: 2016` on a 2016-onward feed) keeps full-snapshot semantics, so a consumer pinned at the start of history still sees the Ministry retire a month. The two floors are orthogonal and both are reported when both fire; `dumps_tracked` vs `dumps_parsed` is what the window excluded. The cost of this shape: a windowed run can never express a removal, so a genuinely-vanished dump stays live until the unwindowed daily run observes it — at most a day late. Note core's own guard cannot cover either case — `detect_removed` "already refuses an *empty* batch; a partial batch is the case that guard does not cover" — and the health downgrade needs `[resilience] enforce` (off by default, documented inert) **plus** `observe_extraction` calls this app does not make.<br>**A missing `hashDumpu` is null and reported, not `""` (2026-09-01):** the hash is the field this app exists to publish, and a renamed or absent tag used to store `hash: ""` / `size_bytes: 0` on every dump - one silent `changed` churn, then permanent blindness to regeneration, invisible to both parse floors because the block still counted as parsed. `hash` and `size_bytes` are now `null` when absent or unparseable, `parse.missing_hash` counts the blind rows, and a `warnings[]` line names them. Deliberately not a skip: a hashless dump is still a listed dump and nothing is tombstoned over it. |

| App(s) | Datasets produced |

| `grants-gov` (daily 09:00), `ca-grants` (daily 09:30), `eu-sedia` (daily 10:00) | own `opportunities` + **`grants/unified`** (canonical schema via `grants-common`, keys `<source>:<id>`: normalized status/dates, honest money — CA `EstAmounts` range → `award_floor`/`award_ceiling`, `EstAvailFunds` → `total_funding`, with K/M/B-suffix + range + thousands parsing — plus `categories[]`, `eligibilities[]` (CA `Categories`/`ApplicantType`, "; "-split), and `aln` (grants.gov `cfdaList`; CA has none). Adding these fields means the first run after deploy re-writes every unified row as `changed`. **`eu-sedia` joined the unified layer 2026-07-16**: its numeric SEDIA status codes are mapped to the canonical `open`/`forecasted` vocabulary, its multi-stage `deadlineDate` array resolves to the earliest still-upcoming cutoff (else the latest, so the sweep can retire it), and its `budgetOverview` is **EUR** — since unified has no currency dimension, eu-sedia's money fields are left `Null` rather than filed as USD. Each run names `grants/unified` in its result `index_datasets`, so every opportunity is an individual full-text search doc (title/agency/status/url) that saved searches can alert on — see [search.md](search.md).<br>**Lifecycle:** both sources are upsert-only (partial views), so a closed/delisted grant just stops appearing — it is never a `removed_at`. After each sync, `grants-common::sweep_closed` flips every live unified row whose status is `open`/`forecasted` and whose `close_date` is before today to `closed` via the normal upsert path (so the transition is a recorded `changed` revision); the run reports `swept`. `removed_at` stays reserved for true full-snapshot sources. **Drift honesty:** a positive server `hitCount`/`total` with zero parsed rows now **fails** the job (was a silent `fetched:0` success); a >50% null-`title` rate across normalized opportunities adds a `warnings` array to the result.<br>**grants-gov sweep honesty (2026-08-13):** the Search2 walk stops for four different reasons and only one of them proves the corpus was covered. The run reports **`sweep`** — `complete` (the records actually **collected** reach the server's own `hitCount` — note this counts records *delivered*, not offsets *requested*, so a page that asked for 1000 and returned 100 can never read as the tail), `capped` (stopped at `maxPages` with records left), `short_page` (a page came back shorter than `rows` while `hitCount` says more remains — a rate-limited or partially-served page, **not** the end), `unknown_total` (`hitCount` was absent/renamed, so it read `0`: the walk now runs on to a short page or the cap instead of stopping after page 1, and coverage is reported as *unproven*). `truncated` is the boolean projection (`sweep != complete`); it used to be computed from the `maxPages` arm alone, so a short page, a mid-sweep `oppHits` drop and a renamed `hitCount` each returned green identically to a full sweep — the renamed-`hitCount` case capped the federal corpus at one page indefinitely. Every non-complete arm also lands in `warnings[]`. Two drift refusals back it: a page the server's own `hitCount` places **inside** the corpus that parses zero `oppHits` fails the job on **every** page (not only the first), and a `hitCount: 0` answer with no hits **while opportunities are already stored** fails as query-grammar drift — but only for an unfiltered query, since a `keyword`/`eligibilities` pull may legitimately match nothing. `errorcode` absent, null or unreadable is no longer treated as success on either endpoint (a stringified `"0"` is accepted as the same integer). One shared date parser (`grants-common::parse_date`, formats `MM/DD/YYYY`, ISO date, ISO/space datetime) backs normalization, the sweep, and the digest.<br>**Deadline timezone honesty:** the canonical `close_date` stays `YYYY-MM-DD` (no consumer/migration impact — every filter, the closing-soon window and the amendment radar are unchanged), but the unified schema gained a sibling **`close_at`**: the deadline as an RFC3339 UTC instant, and **only** where the source published an explicit offset. eu-sedia does (`…T17:00:00Z`, and the multi-stage `deadlineDate` array is now selected on real instants so the chosen cutoff keeps its time of day); grants.gov (`MM/DD/YYYY`) and the CA portal (`2026-11-02 23:59:00`, Pacific but never labelled) do not, so their `close_at` is honestly `Null` — never a zone we invented. Adding the field means the first run after deploy rewrites every unified row as `changed`. The sweep predicate (`is_past_due_open`) now compares a real instant instead of `Utc::now().date_naive()`: **exact** when `close_at` is present, and otherwise the conservative *anywhere-on-Earth* end — midday UTC the day after `close_date`, the first moment no inhabited timezone can still be on that date. Previously a grant closing 23:59 America/Los_Angeles was swept `closed` at 16:59 local and vanished from `?status=open` and `closing-soon` while it was still claimable; the ambiguity now costs at most one extra day of an expired row instead of hiding live money.<br>**Query surface:** `grants/unified` is not just an export — `GET /grants` filters it in SQL by `status`/`agency`/`source`/`close_date` range/`min_award`, and `GET /grants/closing-soon?days=` is the **cross-source** closing-soon view (the job's own `closingSoon` digest is federal-only and built from raw grants.gov hits, so it never sees CA). Both are computed on read from the live corpus — no extra dataset to keep in sync. **Federal money (2026-08-04):** grants.gov's Search2 listing publishes no award amounts (live-verified — an `oppHits[]` entry has only `id, number, title, agencyCode, agency, openDate, closeDate, oppStatus, docType, cfdaList`), which made `min_award` a permanently-empty filter over the largest source. `fetchOpportunity`'s `synopsis` block **does** carry `awardFloor` / `awardCeiling` / `estimatedFunding` (strings, with a literal `"none"` where the agency published nothing), and the detail harvest already parses them into `requirements` via the shared `money_scalar`. `grants_common::enrich_with_detail_amounts` now overlays those figures onto the normalized unified rows **from the stored `grants/opportunity_details` corpus — no extra fetch** — joining on the detail record's own `unified_key`; the run reports `amountsFilled`. The overlay is **fill-only**: it never overwrites an amount the listing already published (ca-grants), and `"none"`/`$0`/prose stay `Null` rather than becoming a matching zero. **The detail harvest is ON by default (2026-08-04), and that default is now stated once (2026-08-13)** — `default_params` carries `harvestDetails: true, maxDetailsPerRun: 50`, so the scheduled daily federal sync feeds the corpus the money join reads. The crate used to state the default three times and contradict itself twice: the module header and the `params_schema` both said ON while the harvest site said `default OFF` above an `unwrap_or(false)`, so the *runtime* default was **false** and only `default_params` supplied true. A caller who built `params` by hand — the documented way to narrow a pull — silently got a different pipeline from the scheduler's, with no warning and no field in the result to notice it by. There is now one constant (`HARVEST_DETAILS_DEFAULT = true`) that both the absent-param path and `default_params` read; an explicit `harvestDetails: false` still turns the stage off, and a non-boolean value falls back to the default rather than being read as a decision. **Known gap (by design):** coverage equals what the harvest has *seen*. The harvest is delta-only (the keys this sync reported new/changed) and capped, so federal `min_award` coverage grows **forward** from the day it was switched on — a corpus-wide backfill of the ~1.4k already-stable opportunities is a deliberate non-goal, and an opportunity that never changes never gains an amount. **The stage is non-fatal to the listing sync, but never silent:** the daily sync's primary obligation is the listing, so a `fetchOpportunity` outage or contract drift no longer fails the job — it is counted into the result's **`detailsFailed`** (with `details: {attempted, failed, abortedAfterConsecutiveFailures, errors[]}` and a `warnings` entry naming the reason). Five back-to-back failures stop the stage early rather than burning the whole cap on a dead endpoint. The strict field-name drift check in `extract_detail` is **unchanged** — drift still produces a named, visible failure, it just degrades the enrichment instead of taking the federal listing down. See [http-api.md](http-api.md)<br>**Source health gating (the unit is the CONTRIBUTION, not the dataset):** `grants/unified` is shared by three sources, so quarantining the *dataset* because one source broke would take the other two down with it — and `AppContext`'s own write gate cannot help, because it resolves health for the write's `(app, dataset)` and `("grants","unified")` is a **virtual pair no `observe_extraction` ever judges** (it always reads `healthy`). So `grants_common::contribution_target` resolves the health of the SOURCE's own pair (`<source-app>/opportunities`) and applies the standard ladder to the shared write: `degraded` → still canonical but stamped **`provisional`**; `quarantined` → diverted to the shadow dataset **`grants/unified@q`**, leaving the canonical layer holding that source's last healthy rows. Same trust vocabulary as everywhere else, so `GET /grants?trust=stable` filters to what we stand behind. The run's `unified` result block reports `{dataset, trust, sourceState}`, and a degrading/quarantined run **withholds `index_datasets` entirely** — the worker's own gate on the virtual pair can never fire, so the producer is the honest place for it. The `sweep_closed` / `link_duplicates` passes are deliberately *not* gated and always write the canonical dataset: they are derived from rows already stored for all sources, not from this run's fetch.<br>**One corpus pass per cycle, not per producer (2026-08-04):** `sweep_closed` and `link_duplicates` are pure functions of the *stored* corpus — identical and idempotent whichever of the three sources triggers them — so running them once per producer bought nothing. Measured against the live store (2637 live `grants/unified` rows: 1787 `open`, 511 `forecasted`, 339 `closed`) the two sweep scans deserialized 2298 rows and the duplicate pass read all 2637 key+simhash rows, **three times every morning**. They now run **once per sync cycle** — the UTC calendar day, which is exactly what the 09:00 / 09:30 / 10:00 schedules share — claimed by whichever source reaches `finalize_unified` first. The claim is one `upsert` of `grants/maintenance` key `corpus_pass`, whose `BEGIN IMMEDIATE` transaction makes the returned change-kind a true compare-and-set: two producers finishing at the same instant cannot both sweep, and a source that fails outright cannot strand the pass (the next one to arrive claims it). Per-day totals drop from 6894 → 2298 swept-row reads and 7911 → 2637 duplicate-pass rows (**−66.7% each**). **Freshness is unchanged**, because each producer still sweeps its own batch in memory (`past_due_in_batch`, zero I/O, same `is_past_due_open` predicate): a source that re-lists an already-expired opportunity still retires it in that same run. The result reports `corpusPass: {ran, cycle, batchSwept, corpusSwept}`, and a run that did **not** own the pass reports `crossSourceDups: null` — never a fabricated `0`, which would claim "there were no duplicates" rather than "we did not look". No new schedule, no maintenance app.<br>**Recurrence is a typed relation, not a tighter threshold (2026-08-04):** one fixed SimHash distance cannot tell *"same program, different portal"* (a true duplicate) from *"same program, next annual cycle"* (not a duplicate at all — the earlier posting is over and the later one is the live opportunity). The corpus pass now classifies every near-duplicate pair deterministically (**no LLM**) and writes the two relations to two datasets: **`grants/duplicate_links`** (unchanged shape, now stamped `relation: "duplicate"`) and the new **`grants/recurrence_links`**. Signals, all from the canonical schema: `aln` — the federal program's own permanent id, a hard veto when both rows publish one and they share no listing; `agency` — a cycle is the same agency re-posting; `title` — must match exactly once the year tokens (`FY2026`, `2026`, `2026-2027`) are stripped, since those are usually the only difference between consecutive cycles; `close_date` — the gap must sit within 45 days of a whole number of years (up to 3); `open_date` — the windows must be **disjoint**, since a program cannot be in its next cycle while the previous one is still accepting applications. **Precision over recall:** any signal short of unanimous falls back to today's behavior — an ordinary duplicate link for a cross-source pair, no link for a same-source pair — because a confident-sounding wrong prediction is worse than none. A recurrence record carries `{program, agency, aln, observed_period_days, period_days, cycles_observed, next_expected_open, next_expected_close, prediction_basis}`. **A next window is never predicted from a single observation:** two postings give one interval, so the period is reported and the next window stays `null` with `prediction_basis` explaining why; only three cycles (two intervals that corroborate each other within tolerance) earn a predicted window, and intervals that disagree earn none. ## `market/profile`: state × trade market profile (N33)

**One row per US state × trade**, keyed `<ST>:<trade>` (`TX:Plumbing`), carrying both halves of *"should I launch as a plumber in Texas, and what will it cost/earn?"*. It is a **join, not a new source**: the join lives in `trades_common::market` (`crates/apps/trades-common/src/lib.rs`) and reads two products this repo already publishes.

**The hazard it removes.** `trades/operator_economics` is keyed `<ST>:<trade>` and `census/market_blend` is keyed `{naics4}:{state_fips}` — `TX:Plumbing` vs `2382:48`. Joining them by hand needs the trade→NAICS map (`taxonomy::TradeEntry.naics`), the USPS→FIPS map (`census_common::state_fips_for_abbr`) *and* the knowledge that the census cell is 4-digit. That is the same class of grain/key hazard the labour trio is warned about at the top of this file, and it now has one answer instead of a warning.

### Two rules the row states about itself

- **`density_grain` is always `naics4`, and it is not a formality.** The nonemployer series publishes no finer grain, so a trade's density is its 4-digit **group's** density. With today's seed taxonomy that means **Plumbing, Electrical and HVAC (all NAICS 238220) share one density block**, and Landscaping and Pool service share another (5617). Their economics differ, so the profiles are distinct — but the density half is a group figure and says so.
- **Coverage is honest, never zeros.** A trade whose group has no blend cell — the census publishes nothing for it, or the census apps have not run — yields `coverage: "economics_only"` with `density`, `succession`, `formation` and `total_market_per_10k` all `null`. A zeroed density block would read as *"nobody operates in this state"* when the fact is *"we did not measure"*.

The `US:<trade>` national roll-up that `trades/operator_economics` also writes is **not** a profile row: it has no state FIPS and therefore can never carry density.

### Who writes it, and when

`sync_market_profile(ctx)` runs at the end of **both** `unified::sync_operator_economics` (the five trades apps) and `app_census_density::sync_market_blend` (the four census apps) — **last writer publishes**, so the product is never a cycle behind either family. **Only `census-density` declares `market/profile` in its result's `index_datasets` today**, which is what lets a watch, trigger, saved search or contract evaluation see its revisions at all. **Known gap, and it is a scope boundary rather than a judgment:** the other eight publishers republish the profile without declaring it, because both shared declaration lists — `census_common::product_index_datasets` and `trades_common::unified::product_index_datasets` — have their exact contents pinned by tests in crates the change that added this product could not touch (`census-nonemp`, `census-nesd`, `census-bfs`, and `app-state-tax`'s `join_is_derived_and_visible` integration test). Closing it is two one-line additions plus four test updates. Until then a refresh driven by one of those eight writes the rows but does not index them, and the next `census-density` run does. `market` is a virtual namespace in `registry::VIRTUAL_NAMESPACES` (publishers: those nine), so it is watchable before its first record and a `[[source]]` row may name it — see [catalog.md](catalog.md).

Writes go through `upsert_many_derived` with **`DerivedPaths` on the replicated national blocks** (`economics.wage_band`, `economics.valuation`, `economics.tax.federal`, `formation`, `vintages.formation_bfs_as_of`): those are the same values on every row, and `formation` moves *weekly*, so without the exclusion one national BFS refresh would mark ~255 profile rows `changed` every Friday. The blocks are still stored and still readable — `DerivedPaths` narrows the change-detection hash and nothing else — and each is announced in its own right by the dataset that owns it. Revisions carry `job_id` and a `derived://market/profile?inputs=…&as_of=…` source URL, never an `artifact_sha`: a joined row has no archived body and must not claim to be replayable. A failed profile publish is **reported on the run's `market_profile` block, never raised** — the rows the run had already written stay written.

### Reading it

- `GET /market/profile/{state}/{trade}` — one row; state code and trade label both matched case-insensitively; `404` names the key it looked for and what publishes the dataset.
- MCP `market_profile {state, trade}` — the same lookup function, read-only and ungated.
- The generic surfaces work too: `GET /datasets/market/profile`, `query_dataset` with `$.coverage:eq:both`-style filters.

### Known gaps (v1)

- **`market/profile` is state × trade, and stays that way.** The blend now also emits COUNTY cells (N35, below), but a county cell carries `state_fips: null` precisely so it cannot enter this join: `build_profiles` indexes cells by `{naics4}:{state_fips}` off the record's own fields, and a county cell that filled that in would replace the state cell behind every profile row. Sub-state grain is read from `census/atlas`, not from here. A `county` argument on `market/profile` is a documented follow-up, not shipped.
- **No currency/inflation adjustment.** Wage, pricing and receipts figures are as published, in their own vintages' dollars; `vintages` is what a consumer deflates by.
- **`density_only` is not a coverage value.** Rows are driven by the economics side, so a blend cell for a state × trade with no economics row produces nothing rather than a density-only profile.
- **Reads the canonical datasets.** If the trades namespace is quarantined its rows divert to `operator_economics@q`, and the profile then joins the last healthy canonical rows rather than the shadow ones.


## `grants/fits`: the applicant fit engine (N31)

`grants/unified` answers "which grants are open". This answers *"which of them can **I** apply for,
and why"* — the question that turns 2600 open opportunities into the fourteen worth reading.

The corpus already carried the fields: unified `eligibilities[]`/`categories[]`/money/`aln`, and the
detail record's `requirements` block with `applicant_types` (honest Null-vs-empty), `cost_sharing`
and `eligibility_text`. Nothing consumed any of them as a *predicate* — the only standing alert over
the corpus was a full-text saved search. The engine lives in
[`grants_common::fit`](../../crates/apps/grants-common/src/fit.rs).

### The two datasets

| Dataset | Key | Written by |
| --- | --- | --- |
| `grants/profiles` | the slugged `name` | `POST /grants/profiles` (an operator, not a scrape) |
| `grants/fits` | `{profile}:{unified_key}` | every grant source's run, over that run's delta |

A profile is `{name, org_type (nonprofit\|gov\|tribal\|smb\|university\|individual), country
(ISO-3166 alpha-2), state?, ein?, uei?, ntee?, budget_band? {min?, max?}, focus_tags[],
cost_share_capacity (true\|false\|null), programs_watched[]}`. Every absent optional field is stored
as an explicit `null` — **absent means UNKNOWN, and unknown never blocks a fit**. Validation is
strict: an unknown field is refused rather than dropped, because a typo'd `cost_share_capacty` that
silently vanishes produces a profile that blocks nothing, matches everything, and never explains
itself. `ein`/`uei`/`ntee` are stored, never verified (IRS EO BMF is still `planned` in the catalog).

**Why a dataset and not a table.** The fit pass runs inside an app, and an app reaches storage only
through `AppContext::datasets` — the dependency rule. A `profiles` SQL table would be invisible to
the very code that exists to read it. Beside that, `grants/fits` has to be a dataset (triggers,
watches, `index_datasets`), so keeping profiles next to it means one storage plane, one export
surface (`GET /datasets/grants/profiles`), and revisions/provenance/doctor/retention coverage for
free. **No migration is used by this feature.**

### The five gates

`fit(profile, unified, detail?) -> {verdict, score, reasons[], blockers[], unknowns[]}` is pure — no
clock, no I/O — so the same corpus and the same profile always produce the same row, which is what
lets a `changed` fit mean real news instead of churn.

| Gate | Passes when | Blocks when | Unknown when |
| --- | --- | --- | --- |
| status | `open` / `forecasted` | `closed` | no status, or one outside the vocabulary |
| geography | the profile's country (and state, for `ca-grants`) matches the source's | a national/sub-national mismatch | the profile names no state; the source has no rule; a non-EU country on `eu-sedia` (third-country participation is decided by call text this v1 does not read) |
| applicant type | a published term maps to the profile's `org_type` | every published term maps, and none matches | `applicant_types` is Null; the agency published `[]`; **any** term is outside the vocabulary map |
| cost share | not required, or required and the profile declares capacity | required and the profile declares **no** capacity | required and the profile **did not say**; the source publishes no requirement |
| award band | the smallest award fits the profile's ceiling, or either side is absent | the award floor exceeds the profile's stated ceiling | *never* |

`verdict` composes them: any blocker → `blocked`; else an undecided **applicant** gate → `unknown`;
else all gates decided → `eligible`; else → `likely`, with every absent field named in `unknowns[]`.
`score` (0.0–1.0) ranks within a band and bands never overlap, so a `likely` can never outrank an
`eligible`; it is rounded to two decimals so a float drifting in the 15th place cannot re-hash the
row and fire a false alert.

### The rules this engine is built around

- **`eligible` needs positive published evidence on every gate.** It is unreachable by absence. The
  failure mode this feature has to avoid is not a missed grant, it is a confident wrong one.
- **A vocabulary miss makes the WHOLE applicant gate unknown**, never a partial verdict over the
  terms we happened to recognise. Dropping the unmapped term is how "3 of 4 terms matched nothing"
  becomes a `blocked` about a sentence nobody read. Misses are counted into the run's `warnings` and
  logged, so the map's blind spots are visible rather than laundered.
- **`[]` is not "nobody is eligible".** The grants-gov normalizer keeps `applicant_types: null`
  (field absent or drifted) apart from `[]` (the agency published an empty list); the read side keeps
  them apart too, and both are `unknown`.
- **A cost-share capacity the profile did not declare is `unknown`, never `blocked`.** Defaulting it
  to `false` would block every match-requiring federal NOFO for every profile that left the field
  out — the single most likely fabricated verdict in the design.
- **The fit row is verdict-shaped.** It copies nothing from the opportunity, so a `changed` revision
  (and the alert it fires) means the fit moved, not that an agency fixed a typo in a title.

### When it runs, and over what

The pass runs on **every** producer, over **that run's delta** — the unified keys it just published
as `new` or `changed` — not over the corpus and not off the once-per-cycle corpus-pass lease. The
lease covers work derived from the *stored* corpus and holds no delta at all, so hanging fits off it
would drop two of the three sources' new grants every day. The engine is pure, so re-scoring an
unchanged opportunity could only produce the identical row: the delta is exactly the set whose
verdict can have moved.

It writes to the **canonical** dataset only. A quarantined source's contribution goes to
`grants/unified@q`, and scoring it would alert on grants the canonical layer does not publish — so a
diverted run reports `fits: null` ("we did not look"), not a zeroed block.

Each run's result carries `fits: {profiles, evaluated, eligible, likely, blocked, unknown, fresh}`.
**`fresh` is the alert set**: the new/changed fit rows. Because `grants` is a registered virtual
namespace, a dataset trigger or watch on `grants/fits` delivers "a grant you are eligible for just
opened" with no new delivery code — see [triggers.md](triggers.md) and
[events-webhooks.md](events-webhooks.md). `grants/fits` joins `index_datasets` only on a run that
actually wrote rows, so an empty window never claims search coverage.

Bounds, all stated rather than silent: `PROFILE_LIMIT` 200 profiles per pass, `FIT_DELTA_LIMIT` 5000
delta keys (the remainder keep their previous verdict and are re-evaluated when the source
republishes them, and the run says so in `warnings`). A profile row whose `org_type`/`country` cannot
be read is **skipped loudly** — no fits at all, rather than fits against a guessed applicant.

### Reading it

`GET /grants/fits?profile=&verdict=&source=`, `GET /grants/profiles`, and `GET /grants?profile=`
(the corpus read through one applicant's verdicts, each hit carrying its `fit` block). See
[http-api.md](http-api.md#get-grantsfits-n31-2026-09-02).

### Known gaps (v1)

- **No Claude refinement over `eligibility_text`.** Every row is `method: "deterministic"`; the field
  exists so a second arm cannot arrive un-named.
- **No EIN verification.** `irs-eo-bmf` ("the eligibility ground-truth") is still `planned`, so
  `ein`/`ntee` are stored and read by nothing. When it ships, a verified 501(c)(3) hardens the
  nonprofit arm of the applicant gate.
- **The vocabulary map is substring-based over two portals' phrasing.** A new portal's taxonomy
  lands in the `unknown` arm — correctly, and visibly — until its terms are added.
- **`eligibilities[]` is empty for `grants-gov` and `eu-sedia`** (neither search hit carries the
  facet), so federal verdicts depend entirely on the detail corpus, which only `grants-gov` writes:
  a federal opportunity with no harvested detail is `unknown`, and that is the honest answer.
- **No fit history.** The row holds the current verdict; the revision log holds the rest.

## `census/atlas`: the sub-state launch atlas (N35)

`census/market_blend` answers *which state*. The atlas answers *which county, and which metro to
price* — the grain people actually open a business in. It is the third product in the virtual
`census` namespace, re-derived at the end of every `sync_market_blend` (so all four census apps
publish it), declared in `census-density`'s `index_datasets`, and cataloged as `census-atlas` with
a contract.

### The geo dimension on the blend

`blend_market` cells are now keyed `{naics4}:{geo_fips}` — a 2-digit state FIPS **or** a 5-digit
county FIPS. **State keys and state rows are byte-identical to before**; county employer rows,
which used to be dropped ("the solo side has no county grain"), now form their own cells. Each cell
says what its solo half actually is:

| `solo_grain` | meaning | `solo_operators` | `total_market` |
| --- | --- | --- | --- |
| `state` | a state cell, both halves at the cell's grain | the count | employer + solo |
| `county` | NES served county rows and they were joined at county | the count | employer + solo |
| `state_carried` | NES published nothing at county grain | **`null`** | employers **only** |

A `state_carried` row also carries `solo_state_operators` — the state's solo total, as labelled
context. It is never apportioned across counties and never enters `total_market`:
a per-county solo number nobody published is exactly the fabrication this family refuses.
`total_market_per_10k_basis` says the same thing in words, and `solo_share` is Null rather than a
`0.0` that would read as "no solo operators here".

### The NES county probe, and its verdict

Whether NES serves `for=county:*` at 4-digit NAICS had never been tested in this repo — the blend
merely asserted it did not. `census-nonemp` now has the probe (`params.geo = "county"`, which
requires a `states` FIPS filter): it issues one keyed request per NAICS and reports
`county_probe: {geo, served, verdicts: [{naics, verdict, status, detail}]}` with one of four
verdicts — `served`, `empty` (204: the grain is accepted, this cell is suppressed),
`unsupported_geography` (the API refused the hierarchy), `http_error`. In county mode a non-rows
answer is the *answer* and the run continues; in state mode nothing changed.

**The probe could not be RUN — no network, no key on the build box — so the recorded verdict is
`ASSUMED UNAVAILABLE`**, pinned in the `census-nonemp` crate doc header the way the BFS contract
was pinned. Everything downstream is built for that answer and needs **no code change** if it is
wrong: the day a keyed run answers `served`, the county rows land in `nonemployers` with
`geo: "county"` and the blend joins them with `solo_grain: "county"`. Settle it with
`POST /jobs {"app":"census-nonemp","params":{"geo":"county","states":"06","naics":["2382"]}}` and
update the header and this section with the LIVE-verified verdict.

### The atlas rows

One row per `(naics4, county)` that entered **either** ranking, keyed `{naics4}:{county_fips5}`:

- **rank 1 — `rank_by_saturation`** over `census/saturation`'s county `per_10k` (establishments per
  10k of the ACS base);
- **rank 2 — `rank_by_total_market_per_10k`** over the blend cell's own density.

Two rankings, not one blended score: they answer different questions and a county can top one and
miss the other, so each row carries both and a **Null** for the ranking it did not enter — never a
position it never reached. `[census] atlas_top_n` (default 25) cuts each independently.

**Every block is grain-labelled**, in one `grains` object, because a county row is four grains
stacked and reads as one measurement otherwise:
`{cell: "naics4|county", employer: "county", solo: "county"|"state_carried",
saturation: "county", succession: "naics_sector", formation: "naics_sector_national",
state_scope: <the basis below>}`.

`metro` is the county's CBSA from the **partial, hand-curated** county→CBSA crosswalk in
`census-common` (`crosswalk_vintage: "omb_2020"`). It covers the principal counties of the large
metros, not the ~1,900-row OMB delineation: a county it does not know gets `metro: null` and is
counted as `unmapped_counties`, never given a substitute market.

### Scope: the top-K states — and what they are actually ranked by

County runs are scoped to the top `[census] atlas_states_k` states (default **10**), and **the
atlas never contains a county outside them** — the one rail that bounds both the dataset and the
CBP request fan-out a county run implies (~3,000 counties × N trades).

The design asked for "the top-K states by formation velocity". **There is no such number.** BFS is
the fleet's only formation source and it publishes at NATIONAL geography only (`for=state:*` is
HTTP 400; every velocity record carries `grain: naics_sector_national`). Apportioning a national
series across states to make a ranking would be the fabrication this product exists to avoid, so
the scope ranks states by the largest signal that IS state-grain — the blend's own `total_market`
summed across trades — and publishes the basis on the run result (`state_rank_basis`) and on every
row (`atlas_state_rank_basis`), so nobody reads it as a formation ranking. Ties break on state
FIPS, so the scope is stable run to run.

### The `metro_pricing` driver

`homewyse-pricing` has always been able to price a metro; nothing chose which metros to pay for.
The atlas now plans them: counties are walked in atlas rank order, folded into their CBSA (one
entry per metro however many of its counties ranked), capped at `[census] atlas_metros` (default
5), and each entry carries a ready `POST /schedules` body —
`{app: "homewyse-pricing", cron, params: {locality: <CBSA title>}, budget_usd}`.

**The plan is always computed and reported; it is only REQUESTED when `[census] metro_pricing` is
on (default `false`).** With the driver off the run publishes
`atlas.metro_pricing: {enabled: false, plan, cap, metros_truncated, unmapped_counties,
crosswalk_counties, requested: 0}` and buys nothing. With it on, the app *asks* the runtime for
each schedule through `AppContext::request_schedule` (the runtime owns the ownership tag, the
`[worker] max_app_schedules_per_run` cap and the fence); refusals are reported as
`refused_by_run_cap`, never dropped silently. `budget_usd` rides the same rail `POST /schedules`
validates and is **omitted** rather than sent as `0` when no ceiling is configured.

### Config (`[census]`)

| key | default | what it does |
| --- | --- | --- |
| `atlas_states_k` | `10` | states the county atlas is scoped to |
| `atlas_top_n` | `25` | counties per trade kept by **each** ranking |
| `atlas_metros` | `5` | metros the pricing plan may name |
| `metro_pricing` | `false` | actually create the planned pricing schedules |
| `metro_pricing_cron` | `0 0 7 1 1,4,7,10 *` | quarterly (the pricing app's own age gate is 90 days) |
| `metro_pricing_budget_usd` | `2.0` | per-run ceiling on each metro schedule; `0` = ask for none |

`census-density` is constructed with the section (`CensusDensity::with_config`); the other three
census apps re-derive the blend through the same entry point with the shipped defaults. Every key
except the cron and the budget is also a per-run param (`atlas_states_k`, `atlas_top_n`,
`atlas_metros`, `metro_pricing`).

### Known gaps (v1)

- **The NES county verdict is ASSUMED, not measured** — see above. Until a keyed run settles it
  every county cell is `state_carried`, i.e. employer-side only.
- **`BLEND_READ_LIMIT` is unchanged at 50,000 per input.** County rows are read as their own
  filtered read (so a county run cannot push the state rows out of a shared recency window) and a
  read that comes back at the cap is reported as `census-density/establishments@county` in
  `inputs_truncated`. Pagination is out of v1.
- **The metro crosswalk is partial and hand-curated.** Unmapped counties are counted, not guessed.
- **A metro-priced row does not reach `trades/operator_economics`**: the unified join looks pricing
  up by `locality == <state code>`. That lookup lives in `trades-common` and teaching it about
  metros is a follow-up.
- **`market/profile` gains no `county` argument in this slice** — deliberately; see the profile's
  own gaps above.

## `transact`: evidence, approval, submit

`transact` runs a declarative browser flow (`steps`: `type`/`click`/`wait_for_selector`/`wait_ms`/`scroll`/`repeat`, reusing `PageAction` verbatim) up to the final confirmation state and **stops before the irreversible action**. `submit_action` lives in its own field, and the staging path has no code path that hands it to the executor — stop-before-submit is structural, not a flag check.

**Params:** `{url, idempotency_key (required, non-blank), submit_action (required PageAction), steps[], profile (`^[A-Za-z0-9_-]{1,64}$`), submit: false, wait_for_selector, confirm_selector, extra_wait_ms (clamped to the render budget, never rejected), max_body_bytes}`.

**Artifacts:** `evidence.json` (the bundle) + `dom.html` (the DOM snapshot at the stop point). The job result carries the same fields minus the DOM. An approved commit additionally writes `receipt.json` + `dom-after.html`.

### The two modes

| `submit` | what happens |
| --- | --- |
| `false` (default) | The dry run. Flow to the confirmation state, evidence bundle, stop. Nothing is staged, nothing can be submitted, the ledger is untouched. |
| `true` | The **same dry run, byte for byte**, plus a `pending` row in the transactions ledger keyed on `idempotency_key`. The job then **parks** ([`waiting`](runtime.md#jobs-that-wait-waiting)) with the bundle as its `input_request`. Only `POST /transactions/{id}/approve` resumes it, and only the resumed attempt can submit. |

`submit: true` was a 422 through M06; it is now a legal *staging* request. It never means "submit now".

### The approval lifecycle

```
enqueue submit:true -> dry run -> pending (ledger) -> job parks (waiting)
                                      |
                    approve ----------+---------- reject
                       |                             |
              job resumes -> re-probe               rejected (terminal)
                       |                             job cancelled
        digest matches -+- digest differs
                |             |
          submit_action   probe_mismatch (terminal refusal, nothing submitted)
                |
        wait confirm_selector -> receipt.json -> submitted (terminal)
```

**States:** `pending` -> `approved` -> `submitted` | `rejected` | `expired`. The last three are terminal; nothing moves a row out of them.

**Routes** (all under the `admin` scope when `[auth] mode = "keys"`, and audited like every mutating verb):

| route | what it does |
| --- | --- |
| `GET /transactions?state=` | The ledger, newest first. Stale `pending` rows are swept first, so a row shown as pending is one the approve door would actually accept. |
| `GET /transactions/{id}` | One row, with a derived `expires_at` and the node's `allow_live`. |
| `POST /transactions/{id}/approve {evidence_sha?}` | Approves and resumes the parked job. `202`. |
| `POST /transactions/{id}/reject` | Rejects and cancels the parked job. Deliberately **not** gated on `allow_live` — an operator who turned live submission off must still be able to close out what it left behind. |

**Why one key can only submit once, ever.** `transactions.idempotency_key` is `UNIQUE` (migration `0046`), so a key owns at most one row for the life of the store. Only a `pending` row is approvable and the approve write is guarded on `state = 'pending'` **in SQL**, so a second approver, a stale tab or an agent retry matches no row. Re-staging a key that already resolved does not reopen it: the run reports the ledger's verdict and finishes instead of parking again.

**What binds an approval to what was reviewed.** `evidence_sha` is SHA-256 over the submit target's identity and clickability and every filled field's selector / found / **length** — never a value, so the digest is safe in a URL, a log or an approval payload while still moving when a password changes. `approve` may quote it (the MCP tool must); a mismatch is a `409`. The commit then re-probes the live page and refuses with `probe_mismatch` unless it *still* hashes to the approved digest. That refusal is terminal, so an approval can never become four attempts at an irreversible action.

**The gates on `approve`, in order:** `[transact] allow_live` (checked first, so a node that has not opted in never reveals which later rule a request broke) -> `admin` scope -> the pure state machine (state, deadline, quoted digest, per-profile 24h cap) -> the SQL guard.

| `[transact]` key | default | meaning |
| --- | --- | --- |
| `allow_live` | `false` | Master switch. Off = every approval is a `409` and no row can ever reach `submitted`. Staging still works, so an operator can see exactly what would be queued. |
| `approval_ttl_secs` | `86400` | How long a `pending` row may wait. **Derived, not stamped** (`created_at + ttl`), so shortening it retires the stale mandates already in the ledger. `0` = never expires. Non-zero by default, unlike `[waiting] expiry_secs`: a parked job waiting forever costs nothing, but an approval waiting forever is a stale mandate one click from acting. |
| `max_submits_per_profile_per_day` | `10` | Rolling-24h submit cap per profile. `0` = no cap. |
| `list_limit` | `100` | Rows `GET /transactions` returns. |
| `webhook_url` / `webhook_secret` | none | Subscriber for `transaction.approved` / `transaction.rejected`. Absent = no delivery; there is no global event subscriber to borrow. |

**MCP:** `list_pending_transactions` (always offered — reading the inbox releases nothing) and `approve_transaction`, which appears only when **both** `[mcp] allow_approve` and `[transact] allow_live` are on and requires `evidence_sha`. See [mcp.md](mcp.md).

### What v1 of the live path deliberately does not do

- **No session-handle resume.** The commit does not inherit the staging run's tab. It **rebuilds the flow deterministically** from the same params under the same profile — twice, in fact: once to re-probe and compare, once to submit, because `render` is one shot and offers no seam at which Rust could look at a page and then decide whether to click. This is why `steps` must be genuinely reversible; that is what makes them steps rather than the submit action.
- **No screenshots.** The render path still exposes no capture, so `screenshot_path` stays `null` in the receipt too — an honest gap, not a stub.
- **No WASM policy predicates for auto-approval.** Every release is a human, or an admin-scoped agent acting through the same door.
- **A commit that did not submit is not recorded as one.** If the receipt says `submitted: false` (the button was gone, the deadline cut the action list), the row stays `approved` and `receipt_path` stays empty.

### Refusals happen at the door, and they fail once

For an app that ACTS on live pages the retry ladder is a hazard, and a permissive front door is worse. Four rules:

- **`submit: true` is no longer refused** (it was, through M06). It is a staging request, and what keeps a staged flow from submitting is not a check but the absence of a code path: `Browser::transact` never appends `submit_action` to the executor's step list. Only `Browser::commit`, reachable only from a ledger row an approval already moved to `approved`, can.
- **A blank `idempotency_key` is a 422** — the schema requires a non-whitespace character (`pattern: "\\S"`), matching what `validate` has always enforced at run time.
- **Unknown top-level params are a 422** (`additionalProperties: false`). A typo'd `"step"` (singular) used to pass the schema, get silently dropped by the deserializer, run a **zero-step flow**, and emit a perfectly plausible landing-page bundle a human might approve off. Keys starting with `_` are exempt (`patternProperties: {"^_": {}}`) because the trigger runtime injects a `_trigger` envelope into a target job's params. Since **trigger-fired enqueues bypass the enqueue-time schema validator entirely** (they go straight to the queue), the app re-checks the same rule at run time with the same underscore allowlist — so a triggered job is neither broken by the rule nor exempt from it.
- **A flow under a profile the vault does not hold is refused before Chrome starts.** Renders create a profile dir on first use — that is the documented onboarding path (`headless = false`, log in once). For a flow that acts, that default was a trap: a typo'd name silently produced an empty, **logged-out** Chrome profile, and the flow ran against a login wall. The error names the profile and points at `GET /profiles` (`has_browser_dir` is the field that matters). Running with no profile at all is still valid.
- **An unsafe `profile` name is a 422 at the door too** (`pattern`: 1–64 chars of ASCII letters, digits, `-`, `_`). The schema's pattern is generated from the engine's own `validate_profile_name` and pinned to it by a test, so the door and the engine cannot disagree about what a legal profile is.

Every one of these refusals is **terminal for the job**: a deterministic refusal fails ONCE instead of riding the whole backoff ladder re-deriving itself on every attempt. Four are typed `Error::Transact`; the unsafe-profile-name refusal is typed `Error::BadRequest` (client input this service understood and rejected — a 400 at the request boundary), which is terminal for the same reason. It used to be an `Error::Profile`, i.e. **retryable**, so a typo'd profile burned four attempts on one sentence; that whole variant is deliberately *not* reclassified, because it also carries genuinely transient cookie-jar IO. The same retype applies on the plain `render` path — the property is policed for both seams by the cross-engine conformance battery (`crates/server/src/e2e/engine_conformance.rs`), not by this sentence. A failure *during* a flow (Chrome died, the page never loaded) is an `Error::Browser` and stays retryable — that boundary is what keeps the classification honest. So is an over-cap DOM on the read-only render path: its cap is fixed but its input is a live page that may be smaller on the next attempt. See [runtime.md](runtime.md).

### The bundle answers a reviewer's questions, not the executor's

The whole product is a bundle a human reads before approving a live submit, so every field is written to be **falsifiable**:

- **`steps: {requested, attempted, completed, deadline_hit, outcomes[]}`** — three different numbers. `requested` is what the caller asked for, `attempted` is what the executor reached (below `requested` only when the flow's time budget ran out, which `deadline_hit` states), and **`completed` counts successes**, never attempts. `outcomes[]` carries one entry per attempted step, in order: `ok` · `selector_missing` (the CSS selector matched nothing) · `action_failed` (the element was there, the interaction was not accepted) · `partial` (the step ran but not to the extent asked: a **`repeat`** block whose passes were not all clean — deliberately coarse, one outcome for the whole block, inner steps are not reported individually so the bundle never claims granularity it does not have — or a **`wait_ms` truncated by the render budget**, `[browser] render_budget_secs`, which clamps caller waits rather than failing the flow). Top-level `steps_completed` mirrors `steps.completed`.
- **`wait_for_selector_found`** — the outcome of the transact-level `wait_for_selector`: `true` it appeared, `false` it never did, `null` none was requested. This is the confirmation state; it used to be computed and thrown away.
- **`submit_target: {selector, found, visible, enabled, tag, label}`** — `submit_action`'s target assessed **on the final page**. `found: null` means the probe could not run (the evaluate failed / the page navigated away) — an honest "we could not look", never conflated with "it is not there". The whole object is `null` when the submit action targets no selector at all (a scroll/wait/repeat). `would_submit` is still echoed verbatim, but echoing it alone can never distinguish a working flow from a broken one — it is identical in both.
- **`filled_fields[]: {selector, value, found, redacted, value_len, truncated}`** — see § Secrets below.
- **`profile`** — the session-vault identity the flow actually ran under (`null` = profile-less). Approving a submit is approving it *as someone*.
- **`dom` (in `evidence.json`): `{artifact, bytes_captured, bytes_stored, truncated}`**, plus a top-level `dom_truncated` in the job result. On the transact path an over-cap DOM is **truncated and flagged**, not fatal: by capture time the flow has already navigated, filled and clicked, so failing the job there would destroy the only record of what a live page was just made to do. The read-only `render` path is unchanged and still **fails closed** on an over-cap DOM (nothing has happened yet there).
- **`nav_timed_out`**, **`screenshot_path`** — unchanged; the latter is always `null` (the browser engine exposes no screenshot capture — an honest gap, not a stub).

### The receipt answers "what did it actually do"

`receipt.json` (and the commit run's job result) is the post-submit half of the same contract:

- **`submitted`** — whether `submit_action` actually ran and succeeded. `false` when the deadline cut the action list before reaching it, or the button was gone by then. The ledger only records `submitted` when this is `true`.
- **`approved_evidence_sha` / `observed_evidence_sha`** — the digest that was approved, and the one the live page produced immediately before the click. Equal on every submitted receipt by construction, and printed anyway: a receipt that cannot be checked is not evidence.
- **`submit_outcome`** — the irreversible action's OWN outcome, reported separately from `steps`, so a successful `type` can never stand in for a click that never happened.
- **`confirm_selector` / `confirm_selector_found`** — the selector asked for as proof of landing, and whether it appeared. Both `null` when none was requested; the receipt does not invent a success.
- **`steps`** — the same honest `{requested, attempted, completed, deadline_hit, outcomes[]}` block, over the re-driven reversible steps only.
- **`dom`** — the post-submit DOM in `dom-after.html`, truncated-and-flagged over the cap for the same reason the staging bundle is: the action already happened.

### Secrets: the summary proves a field was filled, it does not republish it

`filled_fields[]` used to carry every typed field's **live `.value`** — including a password's — into `evidence.json` on disk, the persisted job result, and from there every SSE subscriber, webhook payload and HMAC callback. Now:

- **Masked at capture, in the page.** `input[type=password]`, and any input whose `autocomplete` carries `current-password` · `new-password` · `one-time-code` · `cc-number` · `cc-csc` · `cc-exp` / `cc-exp-month` / `cc-exp-year`, come back as `{value: null, found: true, redacted: true, value_len: <n>}`. The plaintext never leaves the tab, so no artifact, result row or delivery can carry it even in principle. The token list is compiled into the capture script from the Rust constant, so the browser-side and Rust-side predicates cannot drift.
- **Length-capped.** Non-secret values are cut to **512 characters** with `truncated: true` and the real length in `value_len`, so a filled `<textarea>` cannot balloon the result payload. The cap is re-applied on decode, so a value can never slip past it.
- **Shape is additive.** `redacted` / `value_len` / `truncated` are `serde(default)`, so a consumer reading the old `{selector, value, found}` keeps working — but note that a **redacted field's `value` is `null` with `found: true`**, which such a consumer will read as "empty", not "secret".

**Out of scope (deliberately):** the job's **`params`** still contain whatever the caller typed into a `type` step's `text` — params are persisted verbatim for every app, so redacting them is a job-model change, not a transact one. `dom.html` is not redacted either (a password input does not echo its value into the DOM's `value` attribute). Artifacts are not encrypted at rest.

**Known gaps:** no screenshots, no iframe/shadow-DOM traversal, no URL/SSRF policy on the flow's `url`, no session-handle resume across the approval (the flow is rebuilt), no auto-approval policy engine.

## `research`: a living knowledge base

A research run used to leave a job result and a `report.json` artifact and nothing else — the most expensive producer in the fleet was the only one that wrote no dataset. It now writes two, so findings and citations become records that search, watches, triggers, derived datasets, the SDK and peers already know how to consume.

### The two datasets

| dataset | key | record | written when |
| --- | --- | --- | --- |
| `research/findings` | `{slug(topic)}#{index}` | `{topic, index, finding, sources[]}` | `persist` (default **true**) and the report was `structured` |
| `research/sources` | the cited URL | `{url, title, snapshot, snapshot_error}` | same, one per cited URL that survived the cap |

`slug(topic)` is lowercase-alphanumeric with single dashes, capped at 60 chars. It is deterministic on purpose: **that is what makes a re-run update its findings instead of appending a second copy of them.** Nothing per-run (session id, query text, spend, job id) is stored in a record — a per-run value would mark every record `changed` on every run and turn watches, triggers and the yield ledger into a churn feed. The run that produced a revision is recoverable from its provenance `job_id`.

**`topic` is the key space, not the question.** It defaults to `query`. A follow-up run asks something different ("Source X changed, update the findings") but belongs to the same body of knowledge, so it passes the **original** query as `topic` and updates those records rather than forking a second set under its own slug.

Both datasets are declared in the result's `index_datasets`, so their revisions reach the search index and saved-search alerts like any other product dataset.

### Provenance (M12)

- `findings` revisions carry `job_id` only. A finding is synthesis, not a fetched body: it has no `source_url` of its own and never claims one.
- `sources` revisions carry `source_url` always (the cited URL — the post-redirect URL when the body was actually fetched) and `artifact_sha` **only when a snapshot was really saved**. An unarchived citation is not re-derivable, and stamping a hash for it would be exactly the fabrication `Provenance` forbids. `rules_hash` stays Null (no RuleSet is involved), so a source revision never reports `replayable()`.

### Params

| param | default | what it does |
| --- | --- | --- |
| `topic` | the `query` | key space for the findings records |
| `persist` | `true` | write the two datasets at all |
| `snapshot_sources` | `false` | fetch each cited URL through `ctx.fetch` (metered) and save it as `source-N.md`, stamping `artifact_sha` |
| `archive_max_age` | — | snapshots only: accept an archived body up to N seconds old instead of going live |
| `watch_sources` | `false` | create one `watch` schedule per cited URL (`managed_by = "app:research"`), echoed in `watch_requests` |
| `watch_cron` | `0 0 7 * * *` | cron for those watches |
| `max_watched_sources` | `[research] max_watched_sources` (20) | per-run ceiling on **every** per-source action |

**`[research] max_watched_sources`** (default 20) is the operator rail. One cap governs the record write, the snapshot fetch and the watch proposal, so `sources_truncated: true` has a single meaning: this run cited more sources than it acted on. A citation list past 20 is a survey, not a citation set, and every entry past it costs a real metered fetch.

*Plumbed (P.3, wave 4):* `registry::apps(&config)` now takes the loaded config and constructs `Research::with_config(&config.research)`, so the app carries its own `[research]` section and reads the cap off `self`. Precedence is per-run param → the operator's `config.toml` key → the shipped default (20). Editing `[research] max_watched_sources` binds on the next run with no per-run param. This is the general seam: an app that owns a `[section]` is CONSTRUCTED with it in `registry::apps`; apps that own no section are registered exactly as before.

### Snapshots

`snapshot_sources: true` fetches each surviving citation through the **tiered fetcher** — governor, response cache, archive tier, learned tier router, cost ledger — and saves the Markdown as `source-N.md` in the job's artifact dir. The source record then carries `snapshot: {artifact, chars, sha256, fetched_url}` and the revision is stamped with that sha, so the citation can be re-read exactly as it was when the report cited it.

Every failure mode is recorded, never fatal: a fetch error, a 200 that extracts to nothing (the same judgement `watch` and `readable` make), or a failed artifact write all produce `snapshot_error` on the record and a `snapshots.failed` count. The report has already been paid for; losing it because a cited page 404s would re-buy the whole run on the next attempt. Headroom is re-read before **each** snapshot, so a 20-URL citation list cannot walk past the job's ceiling one page at a time.

**This is unrelated to `[claude] self_hosted_tools`.** That switch makes the research *subprocess* fetch through this node's `fetch` MCP tool under a per-job token, during the agentic loop. Snapshots are this app calling `ctx.fetch` itself, after the subprocess is gone, to archive what the report cited. They behave identically with the switch on or off.

### Watched sources: app-declared schedules

`watch_sources: true` asks the runtime for one `watch` schedule per cited URL, and the run echoes exactly what it asked for in `watch_requests`:

```json
{ "app": "watch", "cron": "0 0 7 * * *", "params": { "url": "https://example.com/vat" } }
```

The app still does not write schedules itself. It calls `AppContext::request_schedule(body)`; the worker's **post-run fan-out** applies the requests once the run has finished OK, through `Storage::upsert_managed_schedule` and tagged `managed_by = "app:research"`. Three properties come from the runtime, not the app:

- **Ownership.** The tag is set by the runtime and cannot be smuggled in the body, so an app-declared row can never overwrite a hand-made or catalog-managed schedule that shares an id (the SQL fence). A refused write is counted, not swallowed.
- **Identity.** The row id is derived (content-addressed over requester, target app, cron and canonical params), so a nightly run asking to watch the same URL re-syncs one row instead of minting a schedule a night.
- **A ceiling.** `[worker] max_app_schedules_per_run` (default 20; `0` refuses every app-declared schedule). Past it `request_schedule` answers `false`, the request is **not** echoed in `watch_requests`, and the run reports `watch_requests_truncated: true` — a separate fact from `sources_truncated`, which is about the citation list.

Only a run that finished OK applies its requests: a panicked, timed-out or cancelled attempt will be retried, and a flapping job must not mint a schedule per retry. An invalid cron is refused at the seam (parsed, not shape-checked) rather than stored as a schedule that never fires.

### The follow-up recipe (the trigger half is still manual)

The loop that makes the knowledge base *self-maintaining* is two objects; `watch_sources` now creates the first, and the trigger is still yours to write:

1. The `watch` schedules `watch_sources: true` created above — the cited page is now fingerprinted into `watch/pages` on a cron, with a field-level diff per revision.
2. A trigger on that change, enqueuing `research` back into the same topic:

```json
{
  "on": { "app": "watch", "dataset": "pages" },
  "then": { "app": "research" },
  "params": {
    "topic": "Current Czech VAT registration thresholds for sole traders",
    "query": "Source <url> changed: <diff excerpt>. Update the findings.",
    "session_id": "<the prior run's session_id>",
    "max_budget_usd": 0.25
  }
}
```

`topic` is what keeps the follow-up updating the same records instead of forking a new set; `max_budget_usd` is the per-topic spend rail. See [triggers.md](triggers.md) for the trigger surface itself and for the fan-out caps that bound a noisy source.

### MCP

`deep_research` still enqueues and returns a job id; the awaited result carries `session_id` and `datasets.findings` / `datasets.sources`, which `query_dataset` reads as the agent's memory. See [mcp.md](mcp.md).

### Known gaps (v1)

- **Superseded findings are not removed.** A run that produces 3 findings for a topic that previously had 5 leaves `#3` and `#4` in place. `sync_many` would fix it but is dataset-wide, and `research/findings` holds every topic, so a full-snapshot sync would delete every other topic's records.
- **No trigger is created by the app** (above); `watch_sources` creates the schedules, the trigger half is still a deliberate `POST /triggers`.
- **No `explain` read-only mode** that re-scores existing findings against snapshots without a new session, and `connector-api-watch`'s `change_summary_request` was **not** extracted into a shared `explain-diff` role — it is not a pure move (it carries Personas-specific tag vocabulary and its own caching), so it stays where it is.

## Conventions for new apps

Params defensively parsed from `ctx.params` with documented defaults; stable record keys; `upsert_many` for partial batches vs `sync_many` for full snapshots (removal detection); metered `ctx.fetch`/`ctx.research`; big payloads to artifacts; compact result JSON with new/changed counts (feeds cost-per-fresh-record and trigger summaries).

**`ctx.fetch`, not `ctx.engines.fetch`.** A page fetch goes through `AppContext::fetch`, which meters the call (one cost event per URL, with the winning engine), clamps an `auto_with_research` fetch to the job's remaining `budget_usd` — soft-downgrading to the free tiers when there is none rather than failing — trains the learned tier router, and records/replays the fetch into the job's VCR cassette. Driving `ctx.engines.{fetch,http,browser}` directly loses all four. The raw engines stay public because a dozen callers legitimately need them (a JSON API that wants conditional GET or a byte body, the self-metering crawler, jobless server-side callers), so the guard is an inventory: **every** raw-engine call site is pinned with a count and a reason in `crates/core/tests/fetch_chokepoint.rs`, and adding one fails that test. If your app fetches a *page*, use `ctx.fetch`; if it calls an *API*, add your justified entry to the inventory.

## Output guards (agentic trades apps)

All five trades apps (`trade-wages`, `homewyse-pricing`, `state-tax`, `valuation-multiples`, `state-licensing`) share output guards via the `trades-common` crate:

- **Structured output**: every research request carries a `json_schema` (`claude --json-schema`), so the CLI validates the answer's shape.
- **Salvage**: `trades_common::salvage_json` recovers a fenced or prose-wrapped object from raw text in ONE pass (no metered re-run) when the engine couldn't parse `output.json`.
- **Plausibility** (`trades_common::validate`): bands must be monotone (low ≤ median ≤ high — wage entry/median/experienced hourly+annual, pricing low/median/high, SDE low/median/high), rates ∈ [0,100] (state top marginal, federal SE/QBI/top rates), magnitudes positive (wages, employment, prices, multiples). A record that violates any check is **rejected with per-record reasons** in the result (`rejected` array + `rejected_count`); valid siblings still upsert.
- **Completeness** (`state-tax`): the 50 states + DC are enumerated in code (`US_JURISDICTIONS`); the result reports `states_covered`, `states_expected`, and a `missing_states` list.
- **Freshness gate** (avoids re-paying the priciest path in the product): before the metered `ctx.research` call, each app checks what it already holds and short-circuits with `{skipped, cost_usd: 0}`. `state-tax` and `trade-wages` gate on **vintage** (`year` equality — tax-year / OEWS-vintage facts are frozen once published, so a same-year refresh is pure burn). `homewyse-pricing` and `valuation-multiples` gate on **record age** (`max_age_days`, default 90 — those figures drift within a year); homewyse's age check is scoped to the requested `locality`. `force: true` always re-runs. This lives in the apps (domain freshness), not the core cache (which is request-identity + a 24h TTL).

### Shared result contract (round 21)

All five agentic trades apps emit the same three blocks, kept consistent by
`trades_common::coverage::RESULT_FIELDS` + `unified::RESULT_FIELDS`, which each app's own
`manifest_declares_every_param_it_ships` test asserts against — a sixth app cannot join the family
and quietly omit them.

- **`coverage: {unit, covered, expected, ratio, floor, short, missing}`** — how much of the expected
  roster the run actually returned. `floor` is 0.9; below it `short: true`. `missing` is `null` for a
  count-only roster, never a misleading empty list. `state-licensing` reports it per trade.
- **`warnings: [string]`** — a coverage shortfall, a suppressed removal, or a truncated join input.
  **Near-total rejection is no longer a silent success**: previously only a *fully* empty batch
  errored, so 1 surviving record of 51 was a green run with `rejected_count: 50`.
- **`unified: {dataset, trust, new, changed, unchanged, inputs_truncated, join_complete}`** — the
  `trades/operator_economics` rebuild. `dataset` reads `trades/operator_economics@q` when the
  namespace is quarantined.
- **`index_datasets`** — declares `trades/operator_economics` + `trades/compliance`. This is what
  makes watches, dataset triggers, `enforce_contracts` and search see `trades/*` revisions **at
  all**: the worker's fan-out is scoped by `run_indexed_apps`, so before this the joined product
  five apps exist to produce was invisible to every one of them.

**`state-tax` completeness floor.** `state-tax` is the only app in the family that writes a full
snapshot (`sync_many_with_provenance`), so a partial run used to tombstone every jurisdiction it did
not return — 30 of 51 states deleted the other 21 and reported SUCCESS. A run below the 90% floor now
**suppresses removal detection** and upserts instead. The result always carries `removed`, plus
`removals_suppressed` (a reason string) when the floor engaged. New param `allow_shrink: true`
overrides it for a roster that legitimately shrank — deliberately *not* `force`, which is the
ordinary way to re-run a vintage-gated app and would therefore switch the floor off on exactly the
runs it exists to protect. The join also filters tombstones (`unified::live_records`), so a removed
state can no longer come back as a live joined row.

**Stored numbers mean what they say.** Rates are **percentage points** (`13.3` = 13.3%), stated by
`validate::RATE_UNIT`; a fraction-shaped rate is rejected with a reason rather than silently read as
1330%. Every validated numeric field is stored as a JSON number even when the model quoted it
(`validate::store_numbers`) — a quoted `"13.3"` used to store as a string and then vanish from
`median_state_rate` via `as_f64`. A declared numeric field holding unparseable text stores as `null`.
`income_tax_type` is closed to `none|flat|graduated` via `validate::normalize_choice` and an
unclassifiable value rejects the record. `homewyse-pricing` stores `unit: null` when the model omitted
it (previously fabricated as `"flat"`, turning a $150/hour rate into a $150 flat job).
`state-licensing` reports `cost_usd: null` + `cost_unreported_calls` instead of a `$0.00` that was
indistinguishable from a genuinely free cache hit.

## Dynamic WASM apps

A scraping use case can ship as a **`.wasm` component** instead of a Rust crate + registry edit + rebuild. A component dropped into `[plugins] app_dir` is discovered at boot, validated, and — with `[wasm_apps] enabled = true` — registered as an ordinary `ScrapeApp`: it appears in `GET /apps` with `runnable: true`, is enqueued at the normal door (`POST /apps/<name>/jobs`), runs on the normal worker loop, and inherits budgets, checkpoints, provenance, receipts, triggers and SSE without knowing they exist.

**The contract is a WIT world**, `pumper:app@0.1.0` (`crates/engine-wasm/wit/pumper-app.wit`), versioned from day one because it is a public ABI:

| direction | function | what it is |
| --- | --- | --- |
| import | `fetch(request-json) -> result<string, string>` | `AppContext::fetch` — tiered, governed, budgeted, VCR-recorded |
| import | `upsert-many(dataset, items-json) -> result<string, string>` | `AppContext::upsert_many_with_provenance` — dedup + change detection + health gating |
| import | `checkpoint(state-json) -> bool` / `restore() -> option<string>` | durable execution across attempts |
| import | `save-artifact(name, bytes) -> result<string, string>` | the job's artifacts dir |
| import | `progress(snapshot-json)` / `log(level, message)` | live progress and structured logs |
| export | `describe() -> string` | the JSON manifest `GET /apps` serves |
| export | `run(params-json) -> result<string, string>` | one job; the `ok` arm is the job result |

Everything crossing the boundary is JSON text: the Rust types already have stable serde shapes, and re-declaring them as WIT records would make every field addition a breaking ABI change. **The import table is the sandbox** — there is no socket, no filesystem, no clock and no environment, so a dynamic app cannot reach the network except through the same chokepoint every compiled-in app uses, and a guest that imports anything undeclared **fails to link at load** (typed `missing_export`), never half-runs.

**N10's plugin capabilities do not apply here, deliberately.** A dynamic app's authority already *is* the `AppContext` seams in the table above, granted per job and metered on that job's ledger. The `capabilities` manifest block and the `pumper_http_request` / `pumper_kv_*` imports belong to the **core-module plugin sandbox** — a different guest kind with a different ABI (see [trigger-plugins.md §Capabilities](trigger-plugins.md#capabilities-n10)) — and `pumper:app@0.1.0` is unchanged by them. An app that wants the network already has `fetch`.

**Bounds are per job, not per call** (`[wasm_apps]`, all with defaults): `fuel_per_job` (deterministic instruction ceiling) with `yield_interval` so the guest returns to the runtime periodically and the run is genuinely cancellable; `max_wall_secs` enforced around the call *and* re-checked at every host import; `max_host_calls`, because a guest looping on `fetch` burns host time rather than fuel; `max_payload_bytes`, refused rather than truncated (a half-read body extracted into records is a silent data defect); `max_memory_mb` per instance with `max_concurrent` bounding **live instances**, since a run holds its instance across every host call it awaits. The run's own cost comes back on the job result under `wasm` (`host_calls`, `fetches`, `records_upserted`, `fuel_used`/`fuel_budget`, `memory_bytes`), never on the records — a per-record cost would mark every record changed on every re-run.

**Which build answered.** Every record a dynamic app writes is stamped `rules_hash = <the module's SHA-256>` (its code *is* its rules), the job result carries `module_sha256`, and the listing entry carries `module_sha256` + `world` + `pinned`. A `[[source]]` row with `engine = "wasm"` declares `module_sha256`, and the loader **refuses to register an app whose bytes do not match the pin** — a module swapped under the same filename stops being runnable instead of quietly becoming a different app writing into one dataset's history. See [catalog.md](catalog.md).

**Every not-registered path stays visible and says why**, because a component that vanished from the listing would look like a missing file:

| listing | reason |
| --- | --- |
| `runnable: false`, `requires: ["config:wasm_apps.enabled"]` | `[wasm_apps] enabled = false` (the **default**): running third-party code with fetch and dataset-write authority is an operator decision. Its manifest is deliberately not read — reading one means instantiating the module. |
| `runnable: false` | the catalog pins a different `module_sha256` (both hashes are in the reason) |
| `runnable: false` | `describe()` is not a usable manifest — not an object, an unusable `params_schema`, an unknown `cost_class`, or **an example that fails the app's own schema** (the exact check the server's manifest test runs over every compiled-in app) |
| `runnable: false`, `requires: ["host:component-model"]` | the file is a describe-only **core module**, the older M28 shape: it exports a manifest and no `run`, so there is nothing to execute |

A static app always wins a name clash; a file in a data dir never shadows a compiled-in app. Enqueueing a listed-but-not-runnable name is a typed **409** carrying that entry's own reason.

**Writing one.** `plugins-src/wasm-app-template/` is a working example (fetch a listing → shape rows → `upsert-many` → checkpoint), built and installed with `just plugin-app wasm-app-template`. That recipe needs `wasm-tools` (`cargo install wasm-tools`) for the componentization step, since `cargo build --target wasm32-unknown-unknown` emits a core module. The **host's own ABI gate does not depend on that toolchain**: `crates/engine-wasm/tests/fixtures/echo-app.wat` is a hand-written component that `just test` links, describes and runs on any machine.

**Not in this slice:** `research` and `sync-many` imports, `observe-extraction`, hot-reload of a running module (`POST /plugins/reload` does not swap app components), and the provisioner → module path.

## Known gaps

Census YoY trend layer awaits multi-vintage accumulation.

**`provisioner` automates none of the Path B contract** ([ONBOARDING.md](../../ONBOARDING.md) §5–7, §10). It produces a *proposal* and stops. Every step that makes a source real is still a deliberate human edit:

1. **Create the app crate** (`crates/apps/<app>/`, `impl ScrapeApp`) — the proposal emits `app = ""` and no code.
2. **Register it** in `crates/server/src/registry.rs` and add the workspace/server dependency.
3. **Paste and edit the `[[source]]` row** into `catalog/data-sources.toml`. The app never writes that file, and neither does the promotion route below. The row arrives deliberately inert (`status = "planned"`, empty `cron`), so pasting it verbatim starts nothing; going live means editing `status`, `cron`, `app`, `market`, `category` and `dataset` by hand.
4. **Create the dataset.** `dataset = "proposed:<key>"` is a marker; no dataset exists until the app crate writes one.
5. **Create the schedule** (`POST /schedules`) — the reconciler only picks up `live` rows with a cron.

The proposal's `rule_set` is a *draft*, dry-run against 1–3 sampled pages at one moment in time; it is evidence for a reviewer, not a validated extractor.

### Proposal lifecycle: `GET`/`POST /provisioner/proposals...`

Since 2026-08-04, `confidence`/`verdict`/`sample_stats` are no longer purely advisory: `crates/server/src/routes/provisioner.rs` reads them to drive a real lifecycle over the proposal record, `planned -> validated | failed -> promoted`, without touching any Path B step above.

- **`GET /provisioner/proposals`** lists the backlog (dual-mode, cursor-paged like every other list route) — a summary per proposal (`status`, `expired`, the frozen `verdict`/`accepted`, `catalog_confidence`, sampled `engine`/`url`, `age_secs`), not the full compiled rule set.
- **`POST .../{key}/validate`** re-runs the SAME dry-run harness `run()` used (`app_provisioner::validate_sample`, built on the crate's own `select_sample_body`/`dry_run`) against a **freshly fetched** sample of the proposal's primary URL, deliberately excluding the archive tier so a stale snapshot can never satisfy a validation that exists to catch drift. Updates `status` to `validated`/`failed`.
- **`POST .../{key}/promote`** re-renders the paste-ready TOML fragment server-side (`app_provisioner::catalog_toml`, the exact function `run()` itself calls — one renderer, so the route's fragment and the compile-time `catalog_toml` field can never drift) and sets `status: "promoted"`. Gated by `app_provisioner::may_promote`: a proposal whose best evidence (the latest validation, or — if never validated — the compile-time verdict) says its rule set does not bind is refused with `409`, never handed out as a paste-ready fragment for a draft already known not to work.

Every transition is an ordinary `Datasets::upsert_stamped` call, so it lands in the record's normal revision history (`GET /datasets/provisioner/proposals/history?key=...`) alongside every other change to the proposal. Expiry (`[provisioner] proposal_max_age_secs`, default 30 days) is computed lazily on `GET /provisioner/proposals` rather than stamped by a maintenance tick — nothing downstream needs it to be an eagerly-written fact, matching how `/retention/preview` and `/enforcement/preview` are read-only dry runs rather than background sweeps. Full contract: [http-api.md § Provisioner proposal lifecycle](http-api.md#provisioner-proposal-lifecycle-provisionerproposals).
