# App fleet & domain datasets

Apps are `ScrapeApp` implementations under `crates/apps/*`, registered in `crates/server/src/registry.rs` (adding one: crate + workspace dep + server dep + one registry line). `GET /apps` lists name/description/schedule/requires/ready plus **`default_params`** (the machine-readable defaults); each description documents its params in prose too. A `POST /apps/{name}/jobs` body's `params` **shallow-merges over `default_params`** — setting one key keeps the rest of the defaults, so a manual run matches its scheduled twin (a non-object `params` replaces wholesale).

## Generic apps

| App | What it does |
| --- | --- |
| `readable` | Any URL → clean Markdown via the tiered fetcher |
| `watch` | Visualping-style URL monitor: fingerprint (title/chars/sha256/600-char excerpt) into `pages` keyed by URL; result carries ChangeKind + field diff. Compose with `/schedules` + `/watches` |
| `crawl` | Broad crawler (see [crawling.md](crawling.md)) |
| `extractor` | Fetch a URL + apply a params-supplied extraction RuleSet |
| `plugin` | Run a named WASM extractor plugin over a fetched page |
| `research` | Agentic web research via the Claude engine (roles: research/compose); JSON report. `session_id` param **resumes** a prior run to drill down on its accumulated context (the query becomes a follow-up) instead of re-paying the full agentic loop; `max_budget_usd` caps per-run spend. Durable execution: `turns_per_step` chunks the run into checkpointed steps (default 8) so a crash/reap/suspend resumes the agent session instead of restarting; result carries `stop_reason` (`completed`, `step_cap`, `turns_exhausted`, `budget_exhausted`, `no_session`, `single_call`) so a caller can tell a genuinely finished report from one truncated by a cap — `structured: false` alone can't distinguish them |
| `provisioner` | **Proposal compiler**, not a provisioner: one sentence (`prompt`) → a reviewed `[[source]]` proposal. Researches 1–3 candidate URLs via the Claude engine, samples each through the tiered fetcher (`to_markdown`, archive tier at `sample_archive_max_age`, default 86400s; API recipes on), drafts a declarative `RuleSet` against the primary sample and **dry-runs it through the real extraction engine**, repairing up to `max_iterations` (default 2, cap 5). Emits one record per prompt into **`provisioner/proposals`** (key = the slugified prompt, so a re-compile is a revision, not a duplicate), plus `proposal.json` and `sample-N.{html,md,txt}` artifacts. Record: `{prompt, catalog_row, catalog_toml, rule_set, seeds, samples, cadence, budget, sample_stats, confidence (0–100), confidence_scale, catalog_confidence (1–5), accepted, verdict, provisioned, intended_dataset, iterations, cost_usd}`. **`samples`** carries, per seed, the fetch tier that actually won, which `FetchOutcome` field held the body, its byte count and a `tier:verdict` trace.<br>**Scoring is per-document.** The draft is written against the primary sample, so the accept bar reads *that document only*: a strict majority of its fields must **hold** (the rule bound, and the transform chain did not reduce the value to nothing). The other candidates are **held-out evidence** — `sample_stats.held_out[]` reports `{url, fields_held, fields_total, fields_missing}` per candidate — and never enter the bar, because they are different sites with different markup and adding one must not move the pass threshold. `confidence` is the share of the primary document's fields that hold. **Three degenerate drafts are rejected deterministically**, before any repair spend and whatever the match rate, with the reason in `sample_stats.rejections[]` and the top-level `rejections`: a rule set of nothing but `const` rules (constants always bind, so it would score 100 while reading nothing off the page); an `each` field yielding **0 items on every** document examined (`ContainerEmpty` is not a miss for a *proven* selector, but a draft has no track record); and a field whose selector matched an element the transforms could not coerce (`to_number` over `"Add to cart"` — the wrong-element signature, which the engine has always computed and the dry run used to ignore). A rejected draft scores `confidence = 0`. **The emitted row is inert by construction**: `status = "planned"`, empty `cron`, `app = ""`, `access = "scrape"`, `engine` = the tier that really served the sample, `confidence` on the catalog's documented 1–5 scale, and `dataset = "proposed:<key>"` — a marker, not a resolvable `<app>/<name>` path, because nothing writes it yet. A **rejected** dry run still emits a record, marked `verdict: "rejected"` in the record *and* `REJECTED` in the row's own `notes` (the pasteable TOML fragment is the only artifact a reviewer may read). The metered discovery stage is checkpointed, so a reaped/suspended compile resumes without re-spending it. Params: `{prompt (required), budget_usd, max_iterations, sample_archive_max_age}`. On-demand only — no schedule. The record also carries a `status` field (`planned` at compile time) driven by the `GET/POST /provisioner/proposals...` lifecycle routes — see [http-api.md § Provisioner proposal lifecycle](http-api.md#provisioner-proposal-lifecycle-provisionerproposals) and "Known gaps" below |
| `transact` | Execute a declarative browser flow **dry-run only** and emit an evidence bundle for human review — never the irreversible action. See [§ `transact`: the dry-run evidence bundle](#transact-the-dry-run-evidence-bundle) |
| `hackernews` | HN stories into a change-detected dataset |
| `connector-api-watch` | Watches Anthropic API docs pages: diff + summarize + alert |
| `smlouvy-dump-watch` | Watches the Czech **Registr smluv** bulk-dump index (`data.smlouvy.gov.cz/index.xml`) → one change-detected record per monthly dump (year/month/sha1/size/URL) in `dumps`, keyed by dump URL and **full-snapshot synced** so a re-generated month surfaces as `changed`. Does not download the ~100 MB dumps; `year_from` trims the ~100-dump history. A `dataset` trigger on `fresh` fans a targeted re-download. Daily 05:30. Serves tender-radar (a sibling product), so it's outside Pumper's grant/labor catalog |

| `grants-gov` (daily 09:00), `ca-grants` (daily 09:30), `eu-sedia` (daily 10:00) | own `opportunities` + **`grants/unified`** (canonical schema via `grants-common`, keys `<source>:<id>`: normalized status/dates, honest money — CA `EstAmounts` range → `award_floor`/`award_ceiling`, `EstAvailFunds` → `total_funding`, with K/M/B-suffix + range + thousands parsing — plus `categories[]`, `eligibilities[]` (CA `Categories`/`ApplicantType`, "; "-split), and `aln` (grants.gov `cfdaList`; CA has none). Adding these fields means the first run after deploy re-writes every unified row as `changed`. **`eu-sedia` joined the unified layer 2026-07-16**: its numeric SEDIA status codes are mapped to the canonical `open`/`forecasted` vocabulary, its multi-stage `deadlineDate` array resolves to the earliest still-upcoming cutoff (else the latest, so the sweep can retire it), and its `budgetOverview` is **EUR** — since unified has no currency dimension, eu-sedia's money fields are left `Null` rather than filed as USD. Each run names `grants/unified` in its result `index_datasets`, so every opportunity is an individual full-text search doc (title/agency/status/url) that saved searches can alert on — see [search.md](search.md).<br>**Lifecycle:** both sources are upsert-only (partial views), so a closed/delisted grant just stops appearing — it is never a `removed_at`. After each sync, `grants-common::sweep_closed` flips every live unified row whose status is `open`/`forecasted` and whose `close_date` is before today to `closed` via the normal upsert path (so the transition is a recorded `changed` revision); the run reports `swept`. `removed_at` stays reserved for true full-snapshot sources. **Drift honesty:** a positive server `hitCount`/`total` with zero parsed rows now **fails** the job (was a silent `fetched:0` success); a >50% null-`title` rate across normalized opportunities adds a `warnings` array to the result. One shared date parser (`grants-common::parse_date`, formats `MM/DD/YYYY`, ISO date, ISO/space datetime) backs normalization, the sweep, and the digest.<br>**Deadline timezone honesty:** the canonical `close_date` stays `YYYY-MM-DD` (no consumer/migration impact — every filter, the closing-soon window and the amendment radar are unchanged), but the unified schema gained a sibling **`close_at`**: the deadline as an RFC3339 UTC instant, and **only** where the source published an explicit offset. eu-sedia does (`…T17:00:00Z`, and the multi-stage `deadlineDate` array is now selected on real instants so the chosen cutoff keeps its time of day); grants.gov (`MM/DD/YYYY`) and the CA portal (`2026-11-02 23:59:00`, Pacific but never labelled) do not, so their `close_at` is honestly `Null` — never a zone we invented. Adding the field means the first run after deploy rewrites every unified row as `changed`. The sweep predicate (`is_past_due_open`) now compares a real instant instead of `Utc::now().date_naive()`: **exact** when `close_at` is present, and otherwise the conservative *anywhere-on-Earth* end — midday UTC the day after `close_date`, the first moment no inhabited timezone can still be on that date. Previously a grant closing 23:59 America/Los_Angeles was swept `closed` at 16:59 local and vanished from `?status=open` and `closing-soon` while it was still claimable; the ambiguity now costs at most one extra day of an expired row instead of hiding live money.<br>**Query surface:** `grants/unified` is not just an export — `GET /grants` filters it in SQL by `status`/`agency`/`source`/`close_date` range/`min_award`, and `GET /grants/closing-soon?days=` is the **cross-source** closing-soon view (the job's own `closingSoon` digest is federal-only and built from raw grants.gov hits, so it never sees CA). Both are computed on read from the live corpus — no extra dataset to keep in sync. **Federal money (2026-08-04):** grants.gov's Search2 listing publishes no award amounts (live-verified — an `oppHits[]` entry has only `id, number, title, agencyCode, agency, openDate, closeDate, oppStatus, docType, cfdaList`), which made `min_award` a permanently-empty filter over the largest source. `fetchOpportunity`'s `synopsis` block **does** carry `awardFloor` / `awardCeiling` / `estimatedFunding` (strings, with a literal `"none"` where the agency published nothing), and the detail harvest already parses them into `requirements` via the shared `money_scalar`. `grants_common::enrich_with_detail_amounts` now overlays those figures onto the normalized unified rows **from the stored `grants/opportunity_details` corpus — no extra fetch** — joining on the detail record's own `unified_key`; the run reports `amountsFilled`. The overlay is **fill-only**: it never overwrites an amount the listing already published (ca-grants), and `"none"`/`$0`/prose stay `Null` rather than becoming a matching zero. **The detail harvest is ON by default (2026-08-04)** — `default_params` now carries `harvestDetails: true, maxDetailsPerRun: 50`, so the scheduled daily federal sync feeds the corpus the money join reads. **Known gap (by design):** coverage equals what the harvest has *seen*. The harvest is delta-only (the keys this sync reported new/changed) and capped, so federal `min_award` coverage grows **forward** from the day it was switched on — a corpus-wide backfill of the ~1.4k already-stable opportunities is a deliberate non-goal, and an opportunity that never changes never gains an amount. **The stage is non-fatal to the listing sync, but never silent:** the daily sync's primary obligation is the listing, so a `fetchOpportunity` outage or contract drift no longer fails the job — it is counted into the result's **`detailsFailed`** (with `details: {attempted, failed, abortedAfterConsecutiveFailures, errors[]}` and a `warnings` entry naming the reason). Five back-to-back failures stop the stage early rather than burning the whole cap on a dead endpoint. The strict field-name drift check in `extract_detail` is **unchanged** — drift still produces a named, visible failure, it just degrades the enrichment instead of taking the federal listing down. See [http-api.md](http-api.md)<br>**Source health gating (the unit is the CONTRIBUTION, not the dataset):** `grants/unified` is shared by three sources, so quarantining the *dataset* because one source broke would take the other two down with it — and `AppContext`'s own write gate cannot help, because it resolves health for the write's `(app, dataset)` and `("grants","unified")` is a **virtual pair no `observe_extraction` ever judges** (it always reads `healthy`). So `grants_common::contribution_target` resolves the health of the SOURCE's own pair (`<source-app>/opportunities`) and applies the standard ladder to the shared write: `degraded` → still canonical but stamped **`provisional`**; `quarantined` → diverted to the shadow dataset **`grants/unified@q`**, leaving the canonical layer holding that source's last healthy rows. Same trust vocabulary as everywhere else, so `GET /grants?trust=stable` filters to what we stand behind. The run's `unified` result block reports `{dataset, trust, sourceState}`, and a degrading/quarantined run **withholds `index_datasets` entirely** — the worker's own gate on the virtual pair can never fire, so the producer is the honest place for it. The `sweep_closed` / `link_duplicates` passes are deliberately *not* gated and always write the canonical dataset: they are derived from rows already stored for all sources, not from this run's fetch.<br>**One corpus pass per cycle, not per producer (2026-08-04):** `sweep_closed` and `link_duplicates` are pure functions of the *stored* corpus — identical and idempotent whichever of the three sources triggers them — so running them once per producer bought nothing. Measured against the live store (2637 live `grants/unified` rows: 1787 `open`, 511 `forecasted`, 339 `closed`) the two sweep scans deserialized 2298 rows and the duplicate pass read all 2637 key+simhash rows, **three times every morning**. They now run **once per sync cycle** — the UTC calendar day, which is exactly what the 09:00 / 09:30 / 10:00 schedules share — claimed by whichever source reaches `finalize_unified` first. The claim is one `upsert` of `grants/maintenance` key `corpus_pass`, whose `BEGIN IMMEDIATE` transaction makes the returned change-kind a true compare-and-set: two producers finishing at the same instant cannot both sweep, and a source that fails outright cannot strand the pass (the next one to arrive claims it). Per-day totals drop from 6894 → 2298 swept-row reads and 7911 → 2637 duplicate-pass rows (**−66.7% each**). **Freshness is unchanged**, because each producer still sweeps its own batch in memory (`past_due_in_batch`, zero I/O, same `is_past_due_open` predicate): a source that re-lists an already-expired opportunity still retires it in that same run. The result reports `corpusPass: {ran, cycle, batchSwept, corpusSwept}`, and a run that did **not** own the pass reports `crossSourceDups: null` — never a fabricated `0`, which would claim "there were no duplicates" rather than "we did not look". No new schedule, no maintenance app.<br>**Recurrence is a typed relation, not a tighter threshold (2026-08-04):** one fixed SimHash distance cannot tell *"same program, different portal"* (a true duplicate) from *"same program, next annual cycle"* (not a duplicate at all — the earlier posting is over and the later one is the live opportunity). The corpus pass now classifies every near-duplicate pair deterministically (**no LLM**) and writes the two relations to two datasets: **`grants/duplicate_links`** (unchanged shape, now stamped `relation: "duplicate"`) and the new **`grants/recurrence_links`**. Signals, all from the canonical schema: `aln` — the federal program's own permanent id, a hard veto when both rows publish one and they share no listing; `agency` — a cycle is the same agency re-posting; `title` — must match exactly once the year tokens (`FY2026`, `2026`, `2026-2027`) are stripped, since those are usually the only difference between consecutive cycles; `close_date` — the gap must sit within 45 days of a whole number of years (up to 3); `open_date` — the windows must be **disjoint**, since a program cannot be in its next cycle while the previous one is still accepting applications. **Precision over recall:** any signal short of unanimous falls back to today's behavior — an ordinary duplicate link for a cross-source pair, no link for a same-source pair — because a confident-sounding wrong prediction is worse than none. A recurrence record carries `{program, agency, aln, observed_period_days, period_days, cycles_observed, next_expected_open, next_expected_close, prediction_basis}`. **A next window is never predicted from a single observation:** two postings give one interval, so the period is reported and the next window stays `null` with `prediction_basis` explaining why; only three cycles (two intervals that corroborate each other within tolerance) earn a predicted window, and intervals that disagree earn none. Note that same-source pairs were previously *excluded* outright, so annual cycles produced no link at all — they were a miss, not a false link; the false-link case was the rarer cross-portal one, which the disjoint-window test now catches. Runs report `recurrenceLinks` alongside `crossSourceDups` (both `null` when the run did not own the corpus pass). Query with `GET /datasets/grants/recurrence_links`. |

The stored record and every revision still carry the full block, and a derived-only movement still refreshes the record body (reads never go stale) — it just appends no revision. **The first run after this deploys re-hashes the topics whose stored hash included `history`, so up to `historyJoined` records report `changed` once and then settle.** |
| `cordis` (weekly Mon 07:00) | The **outcomes** half of the EU funding corpus (eu-sedia carries the open-calls half): CORDIS funded Horizon projects, RCN-keyed into `projects`, plus per-topic-family win stats in `topic_stats`. Two-stage — the Search API listing enumerates project ids only (listing dates are template junk, so nothing else is parsed from it), then a per-project detail fetch supplies money (`ecMaxContribution`/`totalCost`), clean ISO dates, the call identifiers from `relations.associations`, and the org roster. `maxProjects` (default 500) caps the *detail* fetches per run, so the ~23k-project corpus is walked over ~46 weekly runs.<br>**The resume cursor is an offset, and only a proven end wraps it.** `cordis/state` key `cursor` holds `next_offset` — an absolute position in the listing — plus its readable `next_page`/`skip_in_page`/`page_size` projection. Runs report **`sweep`**: `complete` (page arithmetic against the listing's own reported total proved the end — the only ending that sets **`corpus_swept: true`** and wraps the cursor to the top), `capped` (stopped at `maxProjects` with corpus left), or `short_page` (a page came back shorter than `pageSize` while the reported total says more remains — a truncated page, **not** the end: the cursor keeps its place and the run reports a `warnings` entry). Previously any short page set both `corpus_swept: true` and reset the cursor to page 1, so one transient truncation threw away weeks of walk while telling the operator the opposite. Because the cursor counts *consumed ids*, a `maxProjects` that is not a multiple of `pageSize` (450/100) leaves the truncated tail for the next run instead of stepping over it for a whole corpus cycle. `startPage` still overrides the cursor and resumes at the **top** of that page. A legacy page-only `state` row is read at the current page size — never a panic.<br>**Drift stays loud, and now covers the empty shapes.** A listing that reports `total: 0` while projects are already stored **fails the run** and leaves the cursor untouched (the documented `/project/frameworkProgramme=` grammar drift returns exactly that, and the stage-2 guard — gated on `attempted > 0` — structurally cannot see it, since a total:0 listing attempts no detail fetch). An empty first page while the arithmetic puts it *inside* the corpus is drift on every run, not just when `startPage == 1`; an empty page *past* a shrunken listing is the ordinary end of a sweep. Attempting detail fetches and normalizing none of them still fails.<br>**`topic_stats` says what its numbers rest on, and its ghosts die.** Each family record carries a **`coverage`** block — `{corpus_aggregated, corpus_total, corpus_swept}` — because for ~46 weeks of every year these are *partial-corpus* aggregates and eu-sedia embeds them verbatim into open Horizon topics: "3 projects funded, mean €2.1M" now distinguishes "3 of the 3 that exist" from "3 out of a corpus we have walked 5% of". `corpus_total` is `Null` when unknown, never a fabricated `0`; there is deliberately **no stamped `as_of`** (the store's own `last_seen` is refreshed on every rollup, so a stamped timestamp would only rewrite every family every week — eu-sedia reads the envelope instead, see below). The rollup is a **complete recompute** over the stored corpus and is therefore written with **`sync_many`**: a family whose projects left the corpus is now **tombstoned** (`stats_removed` in the result) instead of lingering forever as a ghost row. Its one precondition is that the corpus read was not itself truncated — a read that came back at `AGGREGATE_LIMIT` (200,000, ~8.7× the corpus) is a *window*, so removals are switched off for that run and the run reports `aggregate_truncated: true` plus a warning rather than tombstoning every family outside the window. The corpus read also excludes tombstoned project rows (it uses the live-only filtered read; the plain `list` returns removed records). |

## `transact`: the dry-run evidence bundle

`transact` runs a declarative browser flow (`steps`: `type`/`click`/`wait_for_selector`/`wait_ms`/`scroll`/`repeat`, reusing `PageAction` verbatim) up to the final confirmation state and **stops before the irreversible action**. `submit_action` lives in its own field the executor has no code path to run — stop-before-submit is structural, not a flag check — and `submit: true` is rejected outright (live submission needs the human-approval slice: pending-approval transactions + an explicit approve endpoint + dedup on `idempotency_key`).

**Params:** `{url, idempotency_key (required, non-blank), submit_action (required PageAction), steps[], profile, submit: false, wait_for_selector, extra_wait_ms, max_body_bytes}`.

**Artifacts:** `evidence.json` (the bundle) + `dom.html` (the DOM snapshot at the stop point). The job result carries the same fields minus the DOM.

### Refusals happen at the door, and they fail once

For an app that ACTS on live pages the retry ladder is a hazard, and a permissive front door is worse. Four rules:

- **`submit: true` is a 422 at enqueue**, not a failed job minutes later — the schema pins it with `const: false`. (`TransactRequest::validate` still refuses it too; the engine re-validates a third time. Stop-before-submit stays structural regardless.)
- **A blank `idempotency_key` is a 422** — the schema requires a non-whitespace character (`pattern: "\\S"`), matching what `validate` has always enforced at run time.
- **Unknown top-level params are a 422** (`additionalProperties: false`). A typo'd `"step"` (singular) used to pass the schema, get silently dropped by the deserializer, run a **zero-step flow**, and emit a perfectly plausible landing-page bundle a human might approve off. Keys starting with `_` are exempt (`patternProperties: {"^_": {}}`) because the trigger runtime injects a `_trigger` envelope into a target job's params. Since **trigger-fired enqueues bypass the enqueue-time schema validator entirely** (they go straight to the queue), the app re-checks the same rule at run time with the same underscore allowlist — so a triggered job is neither broken by the rule nor exempt from it.
- **A flow under a profile the vault does not hold is refused before Chrome starts.** Renders create a profile dir on first use — that is the documented onboarding path (`headless = false`, log in once). For a flow that acts, that default was a trap: a typo'd name silently produced an empty, **logged-out** Chrome profile, and the flow ran against a login wall. The error names the profile and points at `GET /profiles` (`has_browser_dir` is the field that matters). Running with no profile at all is still valid.

All of these are typed `Error::Transact`, which is now **terminal for the job**: a deterministic refusal fails ONCE instead of riding the whole backoff ladder re-deriving itself on every attempt. A failure *during* a flow (Chrome died, the page never loaded) is an `Error::Browser` and stays retryable — that boundary is what keeps the classification honest. See [runtime.md](runtime.md).

### The bundle answers a reviewer's questions, not the executor's

The whole product is a bundle a human reads before approving a live submit, so every field is written to be **falsifiable**:

- **`steps: {requested, attempted, completed, deadline_hit, outcomes[]}`** — three different numbers. `requested` is what the caller asked for, `attempted` is what the executor reached (below `requested` only when the flow's time budget ran out, which `deadline_hit` states), and **`completed` counts successes**, never attempts. `outcomes[]` carries one entry per attempted step, in order: `ok` · `selector_missing` (the CSS selector matched nothing) · `action_failed` (the element was there, the interaction was not accepted) · `partial` (**`repeat`-only**, deliberately coarse — one outcome for the whole block; inner steps are not reported individually, so the bundle never claims granularity it does not have). Top-level `steps_completed` mirrors `steps.completed`.
- **`wait_for_selector_found`** — the outcome of the transact-level `wait_for_selector`: `true` it appeared, `false` it never did, `null` none was requested. This is the confirmation state; it used to be computed and thrown away.
- **`submit_target: {selector, found, visible, enabled, tag, label}`** — `submit_action`'s target assessed **on the final page**. `found: null` means the probe could not run (the evaluate failed / the page navigated away) — an honest "we could not look", never conflated with "it is not there". The whole object is `null` when the submit action targets no selector at all (a scroll/wait/repeat). `would_submit` is still echoed verbatim, but echoing it alone can never distinguish a working flow from a broken one — it is identical in both.
- **`filled_fields[]: {selector, value, found, redacted, value_len, truncated}`** — see § Secrets below.
- **`profile`** — the session-vault identity the flow actually ran under (`null` = profile-less). Approving a submit is approving it *as someone*.
- **`dom` (in `evidence.json`): `{artifact, bytes_captured, bytes_stored, truncated}`**, plus a top-level `dom_truncated` in the job result. On the transact path an over-cap DOM is **truncated and flagged**, not fatal: by capture time the flow has already navigated, filled and clicked, so failing the job there would destroy the only record of what a live page was just made to do. The read-only `render` path is unchanged and still **fails closed** on an over-cap DOM (nothing has happened yet there).
- **`nav_timed_out`**, **`screenshot_path`** — unchanged; the latter is always `null` (the browser engine exposes no screenshot capture — an honest gap, not a stub).

### Secrets: the summary proves a field was filled, it does not republish it

`filled_fields[]` used to carry every typed field's **live `.value`** — including a password's — into `evidence.json` on disk, the persisted job result, and from there every SSE subscriber, webhook payload and HMAC callback. Now:

- **Masked at capture, in the page.** `input[type=password]`, and any input whose `autocomplete` carries `current-password` · `new-password` · `one-time-code` · `cc-number` · `cc-csc` · `cc-exp` / `cc-exp-month` / `cc-exp-year`, come back as `{value: null, found: true, redacted: true, value_len: <n>}`. The plaintext never leaves the tab, so no artifact, result row or delivery can carry it even in principle. The token list is compiled into the capture script from the Rust constant, so the browser-side and Rust-side predicates cannot drift.
- **Length-capped.** Non-secret values are cut to **512 characters** with `truncated: true` and the real length in `value_len`, so a filled `<textarea>` cannot balloon the result payload. The cap is re-applied on decode, so a value can never slip past it.
- **Shape is additive.** `redacted` / `value_len` / `truncated` are `serde(default)`, so a consumer reading the old `{selector, value, found}` keeps working — but note that a **redacted field's `value` is `null` with `found: true`**, which such a consumer will read as "empty", not "secret".

**Out of scope (deliberately):** the job's **`params`** still contain whatever the caller typed into a `type` step's `text` — params are persisted verbatim for every app, so redacting them is a job-model change, not a transact one. `dom.html` is not redacted either (a password input does not echo its value into the DOM's `value` attribute). Artifacts are not encrypted at rest.

**Known gaps:** no screenshots, no iframe/shadow-DOM traversal, no live submit, no URL/SSRF policy on the flow's `url`.

## Conventions for new apps

Params defensively parsed from `ctx.params` with documented defaults; stable record keys; `upsert_many` for partial batches vs `sync_many` for full snapshots (removal detection); metered `ctx.fetch`/`ctx.research`; big payloads to artifacts; compact result JSON with new/changed counts (feeds cost-per-fresh-record and trigger summaries).

**`ctx.fetch`, not `ctx.engines.fetch`.** A page fetch goes through `AppContext::fetch`, which meters the call (one cost event per URL, with the winning engine), clamps an `auto_with_research` fetch to the job's remaining `budget_usd` — soft-downgrading to the free tiers when there is none rather than failing — trains the learned tier router, and records/replays the fetch into the job's VCR cassette. Driving `ctx.engines.{fetch,http,browser}` directly loses all four. The raw engines stay public because a dozen callers legitimately need them (a JSON API that wants conditional GET or a byte body, the self-metering crawler, jobless server-side callers), so the guard is an inventory: **every** raw-engine call site is pinned with a count and a reason in `crates/core/tests/fetch_chokepoint.rs`, and adding one fails that test. If your app fetches a *page*, use `ctx.fetch`; if it calls an *API*, add your justified entry to the inventory.

## Output guards (agentic trades apps)

All four trades apps (`trade-wages`, `homewyse-pricing`, `state-tax`, `valuation-multiples`) share output guards via the `trades-common` crate:

- **Structured output**: every research request carries a `json_schema` (`claude --json-schema`), so the CLI validates the answer's shape.
- **Salvage**: `trades_common::salvage_json` recovers a fenced or prose-wrapped object from raw text in ONE pass (no metered re-run) when the engine couldn't parse `output.json`.
- **Plausibility** (`trades_common::validate`): bands must be monotone (low ≤ median ≤ high — wage entry/median/experienced hourly+annual, pricing low/median/high, SDE low/median/high), rates ∈ [0,100] (state top marginal, federal SE/QBI/top rates), magnitudes positive (wages, employment, prices, multiples). A record that violates any check is **rejected with per-record reasons** in the result (`rejected` array + `rejected_count`); valid siblings still upsert.
- **Completeness** (`state-tax`): the 50 states + DC are enumerated in code (`US_JURISDICTIONS`); the result reports `states_covered`, `states_expected`, and a `missing_states` list.
- **Freshness gate** (avoids re-paying the priciest path in the product): before the metered `ctx.research` call, each app checks what it already holds and short-circuits with `{skipped, cost_usd: 0}`. `state-tax` and `trade-wages` gate on **vintage** (`year` equality — tax-year / OEWS-vintage facts are frozen once published, so a same-year refresh is pure burn). `homewyse-pricing` and `valuation-multiples` gate on **record age** (`max_age_days`, default 90 — those figures drift within a year); homewyse's age check is scoped to the requested `locality`. `force: true` always re-runs. This lives in the apps (domain freshness), not the core cache (which is request-identity + a 24h TTL).

## Known gaps

Census YoY trend layer awaits multi-vintage accumulation.

**`provisioner` automates none of the Path B contract** ([ONBOARDING.md](../../ONBOARDING.md) §5–7, §10). It produces a *proposal* and stops. Every step that makes a source real is still a deliberate human edit:

1. **Create the app crate** (`crates/apps/<app>/`, `impl ScrapeApp`) — the proposal emits `app = ""` and no code.
2. **Register it** in `crates/server/src/registry.rs` and add the workspace/server dependency.
3. **Paste and edit the `[[source]]` row** into `catalog/data-sources.toml`. The app never writes that file, and neither does the promotion route below. The row arrives deliberately inert (`status = "planned"`, empty `cron`), so pasting it verbatim starts nothing; going live means editing `status`, `cron`, `app`, `market`, `category` and `dataset` by hand.
4. **Create the dataset.** `dataset = "proposed:<key>"` is a marker; no dataset exists until the app crate writes one.
5. **Create the schedule** (`POST /schedules`) — the reconciler only picks up `live` rows with a cron.

The proposal's `rule_set` is a *draft*, dry-run against 1–3 sampled pages at one moment in time; it is evidence for a reviewer, not a validated extractor.

### Proposal lifecycle: `GET`/`POST /provisioner/proposals...`

Since 2026-08-04, `confidence`/`verdict`/`sample_stats` are no longer purely advisory: `crates/server/src/routes/provisioner.rs` reads them to drive a real lifecycle over the proposal record, `planned -> validated | failed -> promoted`, without touching any Path B step above.

- **`GET /provisioner/proposals`** lists the backlog (dual-mode, cursor-paged like every other list route) — a summary per proposal (`status`, `expired`, the frozen `verdict`/`accepted`, `catalog_confidence`, sampled `engine`/`url`, `age_secs`), not the full compiled rule set.
- **`POST .../{key}/validate`** re-runs the SAME dry-run harness `run()` used (`app_provisioner::validate_sample`, built on the crate's own `select_sample_body`/`dry_run`) against a **freshly fetched** sample of the proposal's primary URL, deliberately excluding the archive tier so a stale snapshot can never satisfy a validation that exists to catch drift. Updates `status` to `validated`/`failed`.
- **`POST .../{key}/promote`** re-renders the paste-ready TOML fragment server-side (`app_provisioner::catalog_toml`, the exact function `run()` itself calls — one renderer, so the route's fragment and the compile-time `catalog_toml` field can never drift) and sets `status: "promoted"`. Gated by `app_provisioner::may_promote`: a proposal whose best evidence (the latest validation, or — if never validated — the compile-time verdict) says its rule set does not bind is refused with `409`, never handed out as a paste-ready fragment for a draft already known not to work.

Every transition is an ordinary `Datasets::upsert_stamped` call, so it lands in the record's normal revision history (`GET /datasets/provisioner/proposals/history?key=...`) alongside every other change to the proposal. Expiry (`[provisioner] proposal_max_age_secs`, default 30 days) is computed lazily on `GET /provisioner/proposals` rather than stamped by a maintenance tick — nothing downstream needs it to be an eagerly-written fact, matching how `/retention/preview` and `/enforcement/preview` are read-only dry runs rather than background sweeps.
